# 诊断错误

诊断困难错误的一套纪律。只有明确说明理由时才可跳过阶段。

探索代码库时，如果存在 `GLOSSARY.md`，请阅读它，以清楚了解相关模块；同时检查你要修改区域的 ADR。

## 脱敏

此技能要求你展示命令、输出和捕获的资料。**先对所有秘密信息脱敏**：用 `<REDACTED>` 替代。围绕环境变量构建循环，让凭据留在环境中，不出现在展示内容里。捕获的资料可能带有身份验证标头：只引用能说明问题的行。

如果脱敏后的输出不足以诊断错误，请说明这一点并询问用户。

## 阶段 1：建立反馈循环

**这就是此技能的核心。** 如果你有一个能紧密反映错误的通过/失败信号（确实会在_这个_错误出现时变红），就能找到原因；二分查找、假设检验和插桩都只是使用这个信号的手段。如果没有该信号，再怎么盯着代码看也无济于事。

在此处投入不成比例的精力。**积极行动。发挥创意。拒绝放弃。**

### 构建方法，按大致优先顺序排列

1. 在任何能够触及该错误的接缝处编写**失败测试**：单元测试、集成测试、端到端测试。
2. 针对运行中的开发服务器执行 **Curl / HTTP 脚本**。
3. 使用夹具输入执行 **CLI 命令**，并将标准输出与已知正确的快照进行差异比较。
4. 使用**无界面浏览器脚本**（Playwright / Puppeteer）驱动用户界面，并对 DOM、控制台或网络进行断言。
5. **重放捕获的轨迹**。将真实网络请求、载荷或事件日志保存到磁盘，再通过隔离的代码路径重放。
6. **一次性测试工具**。启动系统的最小子集（单个服务、模拟依赖项），通过一次函数调用运行出错的代码路径。
7. **属性测试 / 模糊测试循环**。如果错误表现为“输出有时不正确”，就运行 1000 个随机输入并查找失败模式。
8. **二分查找测试工具**。如果错误出现在两个已知状态（提交、数据集、版本）之间，则自动执行“在状态 X 启动、检查、重复”，以便运行 `git bisect run`。
9. **差分循环**。将相同输入交给旧版本和新版本（或两种配置），并比较输出。
10. **人工参与测试（HITL）Bash 脚本**。最后手段。如果必须由人点击，则使用 `scripts/hitl-loop.template.sh` 引导用户，让循环仍保持结构化。捕获的输出会反馈给你。

建立正确的反馈循环，就能完成 90% 的修复工作。

### 收紧循环

将循环视作产品。一旦有了一个循环，就要**收紧**它：

- 能否加快循环？（缓存设置、跳过无关初始化、缩小测试范围。）
- 能否让信号更明确？（断言具体症状，而不是断言“没有崩溃”。）
- 能否提高确定性？（固定时间、设定随机数种子、隔离文件系统、冻结网络。）

耗时 30 秒且偶发波动的失败闭环，实际价值微乎其微；2 秒内出结果的确定性闭环才是高效短闭环，是排查缺陷的关键能力。

### 非确定性错误

目标不是得到干净的复现步骤，而是**提高复现率**。重复触发条件 100 次、并行执行、增加压力、缩短时间窗口、插入睡眠。复现率为 50% 的错误可以调试；复现率为 1% 则不行，因此要持续提高复现率，直到可以调试。

### 确实无法建立循环时

停止并明确说明。列出你尝试过的内容。向用户索取：(a) 可以复现错误的环境访问权限；(b) 脱敏后的捕获资料（HAR 文件、日志转储、核心转储、带时间戳的屏幕录像）；或 (c) 添加临时生产环境插桩的权限。没有循环时，**不要**继续猜测原因。

### 完成条件：循环能够变红

当循环**紧凑**且**能够失败**时，阶段 1 才算完成：你能指出**一条命令**（脚本路径、测试调用或 curl 命令），你已经实际运行至少一次（展示调用和已脱敏输出），并且符合以下条件：

- [ ] **能够失败**：它运行实际出错代码路径，并断言**用户描述的确切症状**，因此该错误存在时会失败，修复后会通过。不能只检查“运行时没有报错”，而必须能_捕获这个特定错误_。
- [ ] **确定性**：每次运行都得出相同结果（偶发错误则应按照上述方式提高复现率并加以固定）。
- [ ] **快速**：耗时以秒计，而不是以分钟计。
- [ ] **代理可运行**：可以无人值守地运行；只有在使用 `scripts/hitl-loop.template.sh` 时才需要人在循环中。

如果你发现自己在命令存在之前就开始读代码构建理论，**请停止：直接跳到假设正是此技能要防止的问题。** 没有能够失败的命令，就不能进入阶段 2。

## 阶段 2：复现并缩减

运行循环，观察错误出现时它如何变红。

确认：

- [ ] 循环复现的是**用户**描述的失败模式，而不是附近碰巧出现的另一种失败。错误找错了，就会修错问题。
- [ ] 多次运行都能复现失败（非确定性错误则要有足够高的复现率，才能用于调试）。
- [ ] 已捕获确切症状（错误消息、错误输出、变慢的耗时），以便后续阶段验证修复是否真正解决问题。

### 缩减

循环变红后，将复现步骤缩减到**仍会变红的最小情形**。一次删除一种输入、调用方、配置、数据和步骤；每次删除后重新运行循环，并只保留对失败起关键作用的内容。

为什么要这样做：最小复现能减少阶段 3 中需要考虑的假设（可疑的活动部件更少），并成为阶段 5 中清晰的回归测试。

当**剩下的每个元素都起关键作用**时，缩减才算完成：删除其中任意一个元素都会让循环变绿。

复现并缩减之前，不要继续。

## 阶段 3：提出假设

在测试任何假设之前，先按可能性排序并提出 **3–5 个假设**。只提出一个假设会让人过早接受第一个看似合理的想法。

每个假设都必须**可以证伪**：说明它所作出的预测。

> 格式：“如果 <X> 是原因，那么 <更改 Y> 会让错误消失 / <更改 Z> 会让问题变得更严重。”

如果无法说明预测，这个假设就只是直觉：删除或完善它。

**测试前先向用户展示按可能性排序的列表。** 用户通常掌握相关领域知识，可以立刻重新排序（“我们刚部署了第 3 项更改”），或知道哪些假设已经排除。这是一个成本很低、节省时间很多的检查点。不要因此停下；如果用户暂时不在场，就按你自己的排序继续。

## 阶段 4：插桩

每个探测都必须对应阶段 3 中的某个具体预测。**一次只更改一个变量。**

工具优先顺序：

1. 如果环境支持，使用**调试器 / REPL 检查**。一个断点胜过十条日志。
2. 在能够区分假设的边界添加**有针对性的日志**。
3. 绝不要“记录所有内容再用 grep 查找”。

每条调试日志都要带有唯一前缀，例如 `[DEBUG-a4f2]`。结束时只需一次 grep 就能清理。未标记的日志会残留下来，已标记的日志则应删除。

**性能分支。** 性能退化通常不适合通过日志诊断。先建立基准测量（计时测试工具、`performance.now()`、分析器、查询计划），然后进行二分查找。先测量，再修复。

## 阶段 5：修复并添加回归测试

只有在存在**正确接缝**时，才应在修复前编写回归测试。

正确接缝是指测试能够在调用位置复现实际错误模式。如果唯一可用的接缝太浅（错误需要多个调用方，单个调用方测试却无法覆盖；或单元测试无法重现触发错误的调用链），那么在那里添加回归测试会带来虚假的信心。

**如果不存在正确接缝，这本身就是一项发现。** 代码库的架构缺陷导致无法有效锁定该缺陷。记录这一发现，并在下一阶段提出。

如果存在正确接缝：

1. 在该接缝处将缩减后的复现步骤转换成失败测试。
2. 观察测试失败。如果你通过修改代码或夹具来强制失败，则与未修改的副本执行 `diff`，证明修改确实生效，然后再相信测试。
3. 应用修复。
4. 观察测试通过。
5. 使用原始的（未缩减）情形重新运行阶段 1 的反馈循环。

## 阶段 6：清理

声明完成前，必须完成以下清理：

- [ ] 原始复现步骤不再触发错误（重新运行阶段 1 的循环）。
- [ ] 回归测试通过（或已记录不存在测试接缝）。
- [ ] 已移除所有 `[DEBUG-...]` 插桩（搜索该前缀）。
- [ ] 已删除一次性原型（或移至明确标记的调试位置）。
- [ ] 在提交或 PR 说明中写明最终验证正确的假设，让之后的调试人员能够从中学习。
