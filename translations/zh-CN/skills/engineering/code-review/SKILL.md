对比用户提供的固定参照点与 `HEAD` 之间的差异，分两个方面审查：

- **编码标准（Standards）**：代码是否符合本仓库记录的编码标准？
- **规格说明（Spec）**：代码是否忠实实现了发起此工作的议题或规格说明？

两个方面由**并行子代理**执行，因此彼此不会污染上下文；随后此技能汇总两者的发现。

应该已经向你提供了议题跟踪系统。如果没有，请告知用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 固定参照点

用户所说的任何对象都是固定参照点（提交 SHA、分支名称、标签、`main`、`HEAD~5` 等）。如果用户没有指定，请询问。

记录一次差异命令：`git diff <fixed-point>...HEAD`（三个点表示以合并基点作为比较起点）。同时记录提交列表：`git log <fixed-point>..HEAD --oneline`。

继续之前，确认固定参照点有效（`git rev-parse <fixed-point>`），并且差异非空。引用错误或差异为空时，应在此处失败，而不是等到两个并行子代理内部才失败。

### 2. 确定规格说明来源

按以下顺序查找发起工作的规格说明：

1. 提交说明中的议题引用（`#123`、`Closes #45`、GitLab `!67` 等），按照跟踪系统文档中的工作流获取内容。
2. 用户作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支名称或功能相符的规格说明文件。
4. 如果没有找到任何内容，请询问用户规格说明所在位置。如果用户表示没有规格说明，**规格说明**子代理应跳过审查，并报告“没有可用规格说明”。

### 3. 确定标准来源

在仓库中搜索所有说明代码编写方式的文件。如果存在 `CODING_STANDARDS.md` 或 `CONTRIBUTING.md`，必须将其列入清单。

除了仓库文档所述内容外，“标准”方面还必须始终包含以下**代码异味基准**：Fowler《重构》第 3 章中的固定代码异味集合，即使仓库没有任何文档也适用。此基准有两条约束：

- **仓库规格说明优先。** 仓库中记录的标准始终优先；如果仓库标准认可某种基准会标记的写法，则不报告该异味。
- **始终需要判断。** 每种异味都是带标签的启发式判断（“可能存在 Feature Envy”），绝不是硬性违规。和这里的任何标准一样，跳过工具已经强制执行的内容。

每种异味都按“是什么”→“如何修复”来说明；请在差异中逐一核对：

- **神秘名称**：函数、变量或类型的名称没有说明它的作用或所持内容。→ 重命名；如果找不到合适的名称，说明设计含混不清。
- **重复代码**：更改中的多个代码片段或文件出现相同逻辑结构。→ 提取共同结构，由两处共同调用。
- **Feature Envy**：某个方法访问另一个对象的数据比访问自身数据更多。→ 将此方法移到它所依赖的数据所在对象上。
- **数据团簇**：相同的几个字段或参数总是一起传递（它们应该组成一个类型）。→ 将它们组合成一个类型并传递该类型。
- **基本类型偏执**：使用基本类型或字符串表示本应拥有独立类型的领域概念。→ 为此概念创建一个小型类型。
- **重复分支判断**：更改中的多个位置对相同类型重复使用相同的 `switch` 或 `if` 级联判断。→ 改用多态，或使用两处共享的映射表。
- **霰弹式修改**：一项逻辑更改迫使差异中的许多文件零散地修改。→ 将相关修改集中到一个模块中。
- **发散式修改**：一个文件或模块因多个互不相关的原因而修改。→ 拆分模块，让每个模块只因一个原因而修改。
- **推测式通用性**：增加了规格说明没有要求的抽象、参数或钩子。→ 删除它；在有实际需要前恢复为内联实现。
- **消息链**：出现调用方不应该依赖的长链导航，例如 `a.b().c().d()`。→ 在第一个对象上添加一个方法，将这一串访问封装起来。
- **中间人**：某个类或函数基本只负责继续转发调用。→ 删除它，直接调用真正的目标。
- **被拒绝的继承**：子类或实现类忽略或覆盖了大部分继承内容。→ 移除继承，改用组合。

### 4. 并行启动两个子代理

在前台同时发出两个子代理调用，并汇总它们返回的报告。

**标准子代理的提示**应包含：

- 完整差异命令和提交列表。
- 第 3 步中找到的标准来源文件列表，**以及完整粘贴的第 3 步代码异味基准**（子代理无法从其他地方获取该基准）。
- 简要要求：“按相关文件或代码片段逐一报告：(a) 差异中违反记录标准的每一处位置，引用该标准（文件和规则）；以及 (b) 发现的任何基准异味，注明名称并引用代码片段。区分硬性违规与判断意见：违反记录的标准可能属于硬性违规，但基准异味始终只是判断意见，并且记录的仓库标准优先于基准。跳过工具强制执行的内容。少于 400 词。”

**规格说明子代理的提示**应包含：

- 差异命令和提交列表。
- 规格说明路径或规格说明内容。
- 简要要求：“报告：(a) 规格说明要求中缺失或仅部分实现的内容；(b) 差异中未被要求的行为（范围扩大）；(c) 看似已实现、但实现方式有误的要求。每项发现都引用规格说明原文。少于 400 词。”

如果缺少规格说明，则跳过规格说明子代理，并在最终报告中注明。

### 5. 汇总

将两份报告分别放在 `## Standards` 和 `## Spec` 标题下，原样呈现或只做轻微整理。**不要**合并或重新排序发现，因为这两个方面是刻意分开的（参见_为什么分成两个方面_）。

以一行摘要结束：分别给出每个方面的发现总数，以及该方面最严重的问题（如果有）。不要跨方面选出一个总赢家；这种重新排序正是分开审查要避免的。

## 为什么分成两个方面

一项更改在一个方面可以通过，在另一个方面失败：

- 遵循所有标准但实现了错误功能的代码 → **标准通过，规格说明失败。**
- 完全按议题要求实现但违反项目惯例的代码 → **规格说明通过，标准失败。**

分别报告可以避免一个方面掩盖另一个方面的问题。
