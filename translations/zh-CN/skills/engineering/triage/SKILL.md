# 分流

让项目 issue tracker 中的问题经过一小组分流角色所组成的状态机。

如果本仓库将外部 PR 视为请求入口(参阅 issue tracker 配置)，分流也包含这些 PR：**PR 是附带代码的 issue**，使用相同角色、状态和流程，只有下文标注"对于 PR"的部分略有不同。根据 issue tracker 配置，将单独的 `#42` 确认为 issue 或 PR。

分流期间发布到 issue tracker 的每条评论或问题**都必须**以此免责声明开头：

```
> *This was generated by AI during triage.*
```

## 参考文档

- [AGENT-BRIEF.md](AGENT-BRIEF.md)：如何撰写持久有效的代理工作说明
- [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)：`.out-of-scope/` 知识库的运作方式

## 角色

两种**类别**角色：

- `bug`：功能损坏
- `enhancement`：新功能或改进

五种**状态**角色：

- `needs-triage`：维护人员需要评估
- `needs-info`：正在等待报告者提供更多信息
- `ready-for-agent`：规格完整，已准备好交给 AFK 代理
- `ready-for-human`：需要由人来实现
- `wontfix`：不会采取行动

对于 PR，应根据附带代码评估相同状态：`ready-for-agent` 表示已附上工作说明，代理应当对差异采取下一步行动；`ready-for-human` 表示已准备好交由人合并。

每个经过分流的问题必须且只能带有一个类别角色和一个状态角色。如果状态角色彼此冲突，先标明冲突并询问维护人员，再进行任何其他操作。

这些是规范角色名称。issue tracker 实际使用的标签字符串可能不同。映射表应已提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

状态转换：没有标签的问题通常先进入 `needs-triage`；之后转为 `needs-info`、`ready-for-agent`、`ready-for-human` 或 `wontfix`。报告者回复后，`needs-info` 会回到 `needs-triage`。维护人员可以随时覆盖状态；如果状态转换看起来不寻常，先标明并询问，再继续操作。

## 使用方式

维护人员调用 `/triage`，并用自然语言说明想做什么。理解请求并采取行动。示例：

- "显示所有需要我处理的事项"
- "我们看看 #42"(issue 或 PR)
- "将 #42 转为 ready-for-agent"
- "有哪些内容已准备好交由代理处理？"

## 显示需要处理的内容

查询 issue tracker，并按最早到最新的顺序展示三个类别：

1. **无标签**：从未分流。
2. **`needs-triage`**：正在评估。
3. **自上次分流备注后报告者有活动的 `needs-info`**：需要重新评估。

当 PR 处于范围内时，将外部 PR 纳入这些类别，并在每行标注 `[PR]` 或 `[issue]`。发现阶段只显示**外部** PR(由 issue tracker 配置决定谁算外部人员)，因此协作者尚未完成的 PR 不属于分流工作。这项筛选只适用于发现阶段；明确指定的 PR 无论作者是谁，都要进行分流。

显示数量和每项的一行摘要。让维护人员选择。

## 分流指定的 issue 或 PR

1. **收集上下文。**读取 issue 或 PR 的全部内容(正文、评论、标签、作者、日期；对于 PR 还要读取差异)。分析以前的分流备注，避免重复询问已解决的问题。使用项目领域术语表探索代码库，并遵守相关区域的 ADR。对代码库执行两项检查：(a) **重复功能**：根据领域概念搜索所请求行为是否已实现(不要只搜索请求中的措辞)，并报告搜索过的位置。如果找到，则属于已实现功能，应在第 5 步中标记为 `wontfix`。(b) **先前拒绝**：读取 `.out-of-scope/*.md`，并指出与请求相似的记录。

2. **提出建议。**告诉维护人员你建议的类别和状态，提供理由，并简要概述与请求相关的代码库情况(包括该功能是否已经实现)。等待指示。

3. **验证声明。**开始深入追问前，先检查此声明是否成立。对于错误，按照报告者提供的步骤重现问题。对于 PR，确认差异实现了所声称的内容：检出代码，并运行相关测试或命令。报告结果：确认(包括代码路径)、未能确认，或细节不足(这是强烈表明需要 `needs-info` 的信号)。验证确认后，可以撰写更有力的代理工作说明。

4. **深入追问(如有需要)。**如果请求需要补充细节，分别使用 "grilling" 和 "domain-modeling" 两次调用 Skill 工具，再按每轮一组问题的方式深入追问，使请求变得具体，并在决定确定时立即更新 `GLOSSARY.md`/ADR。

5. **执行结果：**
   - `ready-for-agent`：发布代理工作说明评论([AGENT-BRIEF.md](AGENT-BRIEF.md))。
   - `ready-for-human`：采用相同的代理工作说明结构，但要说明为何不能委派(需要判断、外部访问、设计决定或人工测试)。
   - `needs-info`：发布分流备注(使用下方模板)。
   - 对于 `wontfix`，根据原因关闭问题并添加评论：
     - **已经实现**：代码库已经包含这项改动。指出它所在的位置；**不要**写入 `.out-of-scope/`(知识库用于记录被拒绝的请求，而不是已经构建的功能)。
     - **拒绝(错误)**：礼貌说明原因，然后关闭。
     - **拒绝(功能增强)**：写入 `.out-of-scope/`，在评论中链接该文件，然后关闭(参阅 [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md))。
   - `needs-triage`：应用相应角色。如果已有部分进展，可以添加评论。

## 快速覆盖状态

如果维护人员说"将 #42 转为 ready-for-agent"，就相信他们并直接应用该角色。先确认准备进行的操作(修改角色、添加评论、关闭)，然后执行。跳过深入追问。如果将问题转为 `ready-for-agent` 时未进行深入追问，询问他们是否希望撰写代理工作说明。

## Needs-info 模板

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

深入追问期间已经解决的所有内容都应记录在"established so far"下，以免丢失。问题必须具体且可采取行动，不要写"请提供更多信息"。

## 恢复之前的会话

如果 issue 或 PR 上有之前的分流备注，先阅读备注，检查报告者是否已回答尚未解决的问题，并在继续前展示更新后的情况。不要重新提出已解决的问题。
