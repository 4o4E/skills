# 用户界面原型

在单个路由生成**多个截然不同的用户界面方案**，并通过浮动底栏切换。用户可以在浏览器中切换不同方案，选中一个(或从每个方案中取用部分内容)，然后丢弃其他方案。

如果问题涉及逻辑或状态，而不是外观，则不应使用这个分支。请使用 [LOGIC.md](LOGIC.md)。

## 适用情形

- "这个页面应该是什么样子？"
- "我想在确定之前先看看这个控制面板的几个方案。"
- "设置页面尝试一种不同布局。"
- 用户可能要花一天时间在脑中比较三个含糊模型的任何情况。

## 两种形式：强烈建议优先使用形式 A

当原型**紧贴应用其余部分**时，更容易作出判断：真实页眉、真实侧栏、真实数据、真实信息密度。单独存在的一次性路由就像真空环境：每个方案单独看都不错。只要有合理的现有页面可以承载多个方案，就默认使用形式 A。只有在原型确实找不到合适位置时，才考虑形式 B。

### 形式 A：调整现有页面(优先)

路由已经存在。多个方案在**同一路由**上呈现，并由 `?variant=` URL 查询参数控制。现有数据获取、参数和身份验证都保持不变。只有呈现内容会根据方案切换。这是默认做法，除非有明确理由，否则选它。

如果原型针对的内容目前没有页面，但自然地属于某个现有页面(控制面板的新区域、设置页面的新卡片、现有流程的新步骤)，也属于形式 A。将多个方案挂载到宿主页面中。

### 形式 B：新页面(最后手段)

只有待原型化的内容确实找不到可容纳它的现有页面时，才使用形式 B(例如全新的顶层界面，或无法合理嵌入其他位置的流程)。按照项目已经使用的路由惯例创建**一次性路由**。不要发明新的顶层结构。命名时明确标记为原型(例如在路径或文件名中包含 `prototype`)。使用相同的 `?variant=` 模式。

提交形式 B 前，先检查是否真的不存在可以嵌入其中的页面。空路由会隐藏由有内容的页面展示出的设计问题。

两种形式的浮动底栏完全相同。

## 流程

### 1. 说明问题并选择方案数量

默认使用**3 个方案**。超过 5 个方案就不再是截然不同的选择，只会带来噪声，所以最多允许 5 个。

在一行文字中写明计划，放在原型所在位置或文件开头的注释中：

> "在现有的 `/settings` 路由中，为设置页面制作三个方案，通过 `?variant=` 切换。"

无论用户是否反对，这种方式都能说明计划。

### 2. 生成截然不同的方案

为每个方案编写草稿，并确保符合以下要求：

- 页面目的及其可访问的数据。
- 项目的组件库 / 样式系统(TailwindCSS、shadcn、MUI、原生 CSS 等)。
- 清晰的导出组件名称，例如 `VariantA`、`VariantB`、`VariantC`。

不同方案在**结构**上必须不同：布局、信息层级、主要交互方式都要不同，不能只改颜色。如果三个方案只是稍作修改的卡片网格，那就不是用户界面原型，只是背景装饰。如果两个草稿太相似，就重新制作其中一个，并明确要求"不要使用卡片网格"。

### 3. 连接各方案

在路由中创建单个切换组件：

```tsx
// pseudo-code, adapt to the project's framework
const variant = searchParams.get('variant') ?? 'A';
return (
  <>
    {variant === 'A' && <VariantA {...data} />}
    {variant === 'B' && <VariantB {...data} />}
    {variant === 'C' && <VariantC {...data} />}
    <PrototypeSwitcher variants={['A','B','C']} current={variant} />
  </>
);
```

对于形式 A(现有页面)：保留切换组件上方的所有现有数据获取；每种方案只更改所呈现的子树。

对于形式 B(新页面)：在 `/prototype/<name>` 下的一次性路由中挂载相同的切换组件。

### 4. 构建浮动切换栏

在屏幕底部中央放置小型固定栏，包含三个部分：

- **左箭头**：切换到上一个方案(首尾循环)。
- **方案标签**：显示当前方案键；如果此方案导出了名称，还应显示名称。例如 `B (Sidebar layout)`。
- **右箭头**：切换到下一个方案(首尾循环)。

行为要求：

- 点击箭头会更新 URL 查询参数(使用框架的路由器，例如 Next 中的 `router.replace`、React Router 中的 `navigate` 等)，以便分享方案链接并在重新加载后保持当前方案。
- 键盘上的 `←` 和 `→` 箭头也会切换方案。如果焦点在 `<input>`、`<textarea>` 或 `[contenteditable]` 元素中，则不要截获箭头键。
- 外观应与页面明显不同(例如高对比度圆角长条、柔和阴影)，以便用户清楚它不是被评估设计的一部分。
- 在生产构建中隐藏：使用 `process.env.NODE_ENV !== 'production'` 或等效检查，以免错误合并的原型栏显示给用户。

将切换栏放入单个共享组件，让两种形式都能复用。将组件放在项目中的共享用户界面位置。

### 5. 交给用户

提供 URL(以及 `?variant=` 的值)。用户有空时会切换浏览不同方案。有价值的反馈通常是"我想要 B 的页眉和 C 的侧栏"，这才是他们真正想要的设计。

### 6. 记录结论并清理

最终选定某个方案后，记录结论(选中的方案及其理由)，再按 [SKILL](SKILL.md) 中的说明保存原型。将最终选定的方案合并到业务代码中，其余未采纳方案保留在临时分支，切勿合入主分支：

- **形式 A**：将选定方案合并至现有页面，从主分支中移除未采用的方案与切换悬浮栏。
- **形式 B**：将选定方案确认为正式路由，从主分支中移除临时路由与切换悬浮栏。

完整方案集是一手资料，应保存在一次性分支中，而非丢弃。因为留在主分支中的方案组件和切换栏会很快过时，并让之后的读者感到困惑。

## 反模式

- **方案差异只有颜色或文字。** 这只是微调，不是原型。真正的多个方案在结构上互不相同。
- **不同方案共享太多代码。** 共享 `<Header>` 没问题；共享 `<Layout>` 会破坏原型目的。每个方案都应能自由舍弃现有布局。
- **将方案连接到真实数据更改操作。** 只读原型没有问题。如果方案需要进行更改，就让它使用 stub：问题是"它应该是什么样子"，而不是"后端能否运行"。
- **直接将原型提升到生产环境。** 方案代码是在原型约束下编写的(没有测试、只有最少错误处理)。将其并入正式代码时，应正确重写。
