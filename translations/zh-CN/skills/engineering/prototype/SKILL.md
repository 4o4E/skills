# 原型

原型是用于**回答问题的一次性代码**。问题决定原型的形态。

## 选择分支

根据用户提示、周边代码，或用户是否在线可供询问，确定要回答的问题：

- **"这套逻辑 / 状态模型是否合理？"** → 使用 [LOGIC.md](LOGIC.md)。构建一个可分享的 HTML 单文件，其中包含自由操作按钮和带标签页的引导流程，推动状态机处理那些难以在纸面上推理的情况，供非开发人员操作。
- **"它应该是什么样子？"** → 使用 [UI.md](UI.md)。在单个路由生成多个截然不同的用户界面方案，通过 URL 查询参数切换，并使用浮动底栏。

这两个分支会产生非常不同的成果；选错分支会浪费整个原型。如果问题确实模糊不清，而且无法联系用户，则默认选择更符合周边代码的分支(后端模块 → 逻辑；页面或组件 → 用户界面)，并在原型开头说明此假设。

## 两个分支都适用的规则

1. **从第一天起就是一次性代码，并清晰标记。** 将原型代码放在接近实际使用位置的地方(要原型化的模块或页面旁边)，这样上下文就很明确；命名时让普通读者能看出它是原型，而不是生产代码。对于一次性用户界面路由，遵循项目已有的路由惯例；不要发明新的顶层结构。
2. **运行方式简单。** 用户界面原型从项目任务运行器的一条命令开始：`pnpm <name>`、`python <path>`、`bun <path>` 等。逻辑演示是用户双击打开的 HTML 单文件。无论哪种方式，启动时都不需要动脑。
3. **默认不持久化。** 状态保存在内存中。持久化正是原型要检查的内容，不应成为原型的依赖项。如果问题明确涉及数据库，则使用临时数据库或明确带有"PROTOTYPE, wipe me"名称的本地文件。
4. **不打磨细节。** 不添加测试，不添加让原型能运行所需之外的错误处理，不增加抽象。目的是快速获取信息。
5. **显示状态。** 每次操作之后(逻辑)或每次切换方案之后(用户界面)，都完整打印或呈现相关状态，让用户能看到发生了什么变化。
6. **完成后保存原型。** 将任何经验证的决策并入真实代码，然后把原型本身作为**一手资料**保存：将其提交到一次性分支，而非主分支；并在实现议题中留下指向该分支的上下文指针。同时也要在议题或提交中记录得到的答案(结论和解决的问题)。主分支只保留经验证的决策。
