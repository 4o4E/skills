# 逻辑原型

创建一个独立 HTML 文件（**可分享的演示**），让任何人都能点击按钮操作状态模型。用户提出的问题涉及**业务逻辑、状态转换或数据结构**时使用：在纸面上看似合理、但只有实际尝试各种情况才会发现问题的内容。

文件只有一个，也无需安装任何内容，因此你可以将它交给非开发人员（设计师、产品经理、领域专家），让他们亲自体验模型。所以原型应使用他们熟悉的语言，而不是代码语言。

## 适用情形

- “我不确定在 X 后执行 Y 时，这个状态机是否能处理这个边缘情况。”
- “这个数据模型真的能表达这种情况吗？”
- “我想在编写代码之前先体验一下这个 API 应该是什么样子。”
- 任何用户想**点击按钮并观察状态变化**的情况。

如果问题是“它应该是什么样子”，则不应使用这个分支。请使用 [UI.md](UI.md)。

## 流程

### 1. 说明问题

编写代码之前，写下要制作原型的状态模型和待回答的问题。将这段说明放在演示开头，作为可见介绍，而不只是代码注释。回答了错误问题的逻辑原型毫无价值，因此要明确写出问题，让用户无论现在是否正在观看或之后才回来都能进行核对。

### 2. 将逻辑隔离到可移植模块

在单个 `<script>` 块中，将实际逻辑（用于回答问题的部分）写成简洁的纯模块，以便将来可以移入真实代码库。页面本身是一次性内容；该模块不是。

正确形态取决于具体问题：

- **纯 reducer**：`(state, action) => state`。适用于操作属于离散事件且状态只有一个值的情况。
- **状态机**：显式列出状态和转换。适用于“当前哪些操作是合法的”本身就是待解决问题的情况。
- **一组纯函数**：针对普通数据类型进行变换。适用于没有隐式当前状态、只有各种转换的情况。
- **具有清晰方法形式的类或模块**：适用于逻辑确实要持有持续状态的情况。

根据正在回答的问题选择最合适的形态，**不要**只选择最容易连接页面的形态。保持纯粹：不要使用 DOM，不要使用 `document`，也不要让按钮处理程序访问模块内部。由页面调用模块；数据流不能反向流动。这样原型在自身使用期限结束后仍然有用：问题得到回答后，经验证的 reducer / 状态机 / 函数集可以直接移入真实模块。

### 3. 构建可分享的 HTML 文件

使用单个 HTML 文件，只写原生 HTML/CSS/JS：不使用框架、捆绑工具或服务器；所有内容都写在文件内，以便双击即可打开，也方便通过电子邮件传阅。任何人都应该能够通过打开文件运行它。

为非开发人员编写。所有标签都使用**领域语言**而非代码语言：按钮和状态应使用业务术语，而不是 reducer 术语。用简单的文字说明发生了什么。

从上到下采用清晰的层级布局：

1. **标题和一句话说明**，说明此演示让用户探索什么（步骤 1 中写出的问题）。
2. **当前状态**：以便于阅读的面板呈现完整相关状态（使用带标签的字段，不要直接输出原始 JSON）；每次点击后重新呈现，让用户看到变化。在有助于非开发人员理解时，指出刚才发生了什么变化。
3. **自由操作按钮**：每个操作始终对应一个可用按钮，让任何人都可以按任意顺序试用模型。每次点击都会分派相应操作并重新呈现状态。
4. **引导流程**：每个标签页对应一组**情境**。每个标签页都包含简短的普通语言说明，描述此情境的初始情况和观察要点；下方按顺序显示该情境中要点击的**按钮**。每一步都是实际按钮；点击后执行该操作并转到下一步。开始引导流程时，应重置到已知的初始状态，确保情境每次运行结果相同。

选择能展示棘手情形的情境，包括正确流程、复杂边缘情况，以及不应允许的操作尝试。

外观精美但克制：字体清晰、间距充足、一种强调色。不使用动画或花哨效果：不要让状态和按钮之外的内容分散注意力。

### 4. 交给用户

将文件交给用户，或为用户打开文件。用户有空时会点击体验引导流程和自由操作；值得关注的反馈通常是“等等，这不应该发生”或“咦，我以为 X 会不一样”。这些就是想法本身的错误，正是制作原型的目的。如果用户想增加操作或情境，就添加这些内容。原型会不断演进。

### 5. 保存答案和原型

原型回答问题后，先记录答案，再按 [SKILL](SKILL.md) 中的说明保存原型。逻辑相关的对应内容是：经验证的 reducer / 状态机 / 函数集移入真实模块（吸收设计决策）；HTML 外层放到一次性分支，使原型作为一手资料得以保存。文件是一个独立文件，因此仍可在该分支中轻易重跑。

## 反模式

- **不要添加测试。** 需要测试的原型就不再是原型。
- **不要连接真实数据库。** 除非问题专门涉及持久化，否则使用内存状态。
- **不要泛化。** 不要考虑“以后如果要支持 X 怎么办”。原型只回答一个问题。
- **不要混淆逻辑和页面。** 如果纯模块引用 DOM、`document` 或按钮处理程序，它就不能再移植。让页面仅作为纯模块的薄外层。
- **不要使用框架、捆绑工具或服务器。** 接收者应该能双击打开单文件；使用 React 应用或开发服务器会破坏可分享的特性。
- **不要将 HTML 外层提交到生产环境。** 该页面是在原型约束下编写的（没有测试，只有最少错误处理）。将它并入正式代码时，应正确重写。
