# 加深模块

根据依赖关系，安全地加深一组浅层模块。本文使用 [SKILL.md](SKILL.md) 中的词汇：**模块**、**接口**、**接缝**、**适配器**。

## 依赖类别

评估候选加深对象时，先对它的依赖分类。类别决定如何通过接缝测试加深后的模块。

### 1. 进程内

纯计算、内存状态、无输入输出。始终可以加深：合并这些模块，并直接通过新接口进行测试。无需适配器。

### 2. 可在本地替代

具有本地测试替代品的依赖(Postgres 对应 PGLite，或内存文件系统)。如果存在替代品，则可以加深。测试套件运行时使用该替代品来测试加深后的模块。接缝位于模块内部；模块的外部接口无需提供端口。

### 3. 自有的远程服务(端口与适配器)

你通过网络边界访问的自有服务(微服务、内部 API)。在接缝处定义一个**端口**(接口)。深层模块拥有逻辑；传输方式作为**适配器**注入。测试使用内存适配器。生产环境使用 HTTP/gRPC/队列适配器。

建议表述："在接缝处定义端口，为生产环境实现 HTTP 适配器，并为测试实现内存适配器。这样即使代码部署在网络两端，逻辑仍集中在一个深层模块中。"

### 4. 真正的外部依赖(模拟)

不由你控制的第三方服务(Stripe、Twilio 等)。加深后的模块接收注入的外部依赖端口；测试提供模拟适配器。

## 接缝纪律

- **一个适配器代表假设中的接缝。两个适配器代表真实接缝。** 至少有两个适配器确有必要(通常分别用于生产和测试)时，才引入端口。只有一个适配器的接缝只是间接调用。
- **内部接缝和外部接缝。** 深层模块可以同时具有实现内部的接缝(供模块自身测试使用)和接口处的外部接缝。不要仅仅因为测试会用到内部接缝，就通过接口公开这些接缝。

## 测试策略：替换，不叠加

- 加深后的模块接口已有测试后，针对浅层模块编写的旧单元测试就没有价值了；删除它们。
- 在加深后的模块接口处编写新测试。**接口就是测试面**。
- 测试应通过接口断言可观察结果，而不是内部状态。
- 测试应能经受内部重构，因为它描述的是行为，而非实现。如果实现变化就必须修改测试，那么测试越过接口了。
