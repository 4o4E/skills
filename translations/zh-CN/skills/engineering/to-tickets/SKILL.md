# 拆分为工单

将计划、规格说明或对话拆分为一组**工单**：每张工单都是曳光弹(tracer bullet)式的纵向切片，并声明有哪些工单会**阻塞**它。

issue tracker 和分流标签词汇应已提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。

## 流程

### 1. 收集上下文

根据当前对话上下文开展工作。如果用户传入了引用(规格说明路径、问题编号或 URL)作为参数，获取该引用并阅读完整正文和评论。

### 2. 探索代码库(可选)

如果你尚未探索代码库，就探索它以了解代码当前状态。工单标题和描述应使用项目领域术语表中的词汇，并遵守你正在处理区域的 ADR。

寻找预先重构代码以简化实现的机会。"先让改动变简单，再完成简单的改动。"

### 3. 起草纵向切片

将工作拆分为**曳光弹**工单。

<vertical-slice-rules>

- 每个切片都要贯穿各层，形成一条狭窄但**完整**的路径(数据结构定义(schema)、API、界面、测试)：纵向切分，**不得**将单层工作横向切分
- 每个已完成的切片都可以独立演示或验证
- 每个切片的规模都应适合在一个全新的上下文窗口中完成
- 任何预先重构都应先完成

</vertical-slice-rules>

为每张工单标明其**阻塞关系**：哪些其他工单必须先完成，它才能开始。没有阻塞项的工单可以立即开始。

**大范围重构**是纵向切分的例外。**大范围重构**指一个机械式改动(重命名列、改变共享符号的类型等)，其**影响范围**遍及整个代码库，因此一个编辑会同时破坏数千个调用点，无法以任何纵向切片保持通过状态。不要强行将它拆成曳光弹；应按照**扩展与收缩**的顺序安排。先扩展：在旧形式旁边添加新形式，确保没有内容损坏。然后分批迁移调用点，按影响范围划分批次(每个软件包或目录一批)，每批一张受扩展工单阻塞的工单；旧形式仍然存在，因此每一批都应让持续集成保持通过。最后收缩：待所有调用者都迁移后，在一张受每个迁移批次阻塞的工单中删除旧形式。如果各批次无法单独保持通过，则保留这个顺序，但让它们共用一个集成分支，并全部阻塞最终的集成与验证工单；只有最终工单保证通过。

### 4. 向用户确认

以编号列表展示建议的拆分。每张工单都显示：

- **标题**：简短且具描述性的名称
- **阻塞项**：必须先完成的其他工单(如果有)
- **交付内容**：这张工单会实现的端到端行为

询问用户：

- 拆分粒度是否合适？(太粗 / 太细)
- 阻塞关系是否正确：每张工单是否只依赖真正阻碍它的工单？
- 是否应该合并某些工单，或进一步拆分？

反复调整，直到用户批准拆分。

### 5. 将工单发布到已配置的 issue tracker

发布已经批准的工单。**具体方式**取决于 `/setup-matt-pocock-skills` 配置的 issue tracker；无论使用哪种方式，工单本身都相同，只是阻塞关系的表达形式不同：

- **本地文件** → 在 `.scratch/<feature-slug>/issues/<NN>-<slug>.md` 下为每张工单写入一个文件，按依赖顺序从 `01` 开始编号(先列阻塞项)。每个文件的"Blocked by"列出它依赖的编号和标题。使用下方的单工单文件模板：每个文件一张工单，绝不使用合并工单文件。
- **真实 issue tracker(GitHub、Linear 等)** → 按依赖顺序发布每张工单(先发布阻塞项)，以便每张工单的阻塞关系都能引用真实标识符。平台有原生阻塞关系时使用它；否则在每张工单中设置"Blocked by"，列出阻塞问题。如果来源是现有问题，将每张工单设为其子问题(参阅 issue tracker 文档中的操作)。应用 `ready-for-agent` 分流标签，除非另有指示；这些工单按其定义即可由代理领取。

按**前沿**推进：所有阻塞项均已完成的工单。若只有一条线性依赖链，前沿就是从上到下依次推进。

不要关闭或修改任何父问题。
