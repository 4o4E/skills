# ADR 格式

ADR 存放在 `docs/adr/` 中，并使用连续编号：`0001-slug.md`、`0002-slug.md` 等。

仅在需要第一个 ADR 时才创建 `docs/adr/` 目录。

## 模板

```md
# {决策的简短标题}

{用 1 到 3 句话说明背景、决定了什么以及原因。}
```

仅此而已。ADR 可以只有一个段落。记录决策已经作出以及作出决策的原因才有价值，不必填满各个章节。

## 可选章节

只有在确实能带来价值时才加入这些章节。大多数 ADR 不需要它们。

- **状态** frontmatter(`proposed | accepted | deprecated | superseded by ADR-NNNN`)：当决策可能重新审议时有用
- **考虑过的选项**：只有在值得记住被拒绝的替代方案时才加入
- **后果**：只有在需要指出不明显的后续影响时才加入

## 编号

扫描 `docs/adr/`，找到当前最高编号并加一。

## 何时提出创建 ADR

以下三项必须全部成立：

1. **难以撤销**：以后改变主意的代价不容忽视
2. **没有背景时会令人意外**：未来的读者看到代码会想"为什么要这样做？"
3. **确实存在取舍**：有真正可行的替代方案，并且你基于具体原因选择了其中一个

如果某个决定容易撤销，就跳过 ADR：你之后直接撤销即可。如果决定并不令人意外，就没人会追问原因。如果没有真正的替代方案，也就没有什么需要记录，除了"我们采用了显而易见的做法"。

### 符合条件的内容

- **架构形态。**"我们使用单一代码仓库。""写入模型采用事件溯源，读取模型投影到 Postgres。"
- **上下文之间的集成模式。**"Ordering 和 Billing 通过领域事件通信，而不是同步 HTTP。"
- **会造成锁定的技术选择。**数据库、消息总线、身份验证服务提供商、部署目标。不是每个库都需要记录，只记录更换时需要一个季度的那些选择。
- **边界和范围决定。**"Customer 数据由 Customer 上下文拥有；其他上下文只能通过 ID 引用。"明确的否定和肯定同样有价值。
- **有意偏离显而易见的路径。**"由于 X，我们使用手写 SQL 而不是 ORM。"任何合理读者会认为你应该反过来做的情况都属于此类。这样可以防止下一位工程师"修正"有意为之的设计。
- **代码中看不出来的限制。**"由于合规要求，我们不能使用 AWS。""由于合作伙伴 API 合同，响应时间必须低于 200ms。"
- **被拒绝且拒绝理由不明显的替代方案。**如果你考虑过 GraphQL，但由于不明显的原因选择了 REST，请记录下来；否则六个月后就会有人再次建议使用 GraphQL。
