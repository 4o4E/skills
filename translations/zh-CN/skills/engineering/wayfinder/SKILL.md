一个松散的想法出现了，它太大，无法在一个代理会话中处理，并且笼罩在迷雾中：从当前位置通向**目的地**的路径尚不可见。Wayfinding 旨在找出这条路径，而不是直接冲向目的地。此技能会在仓库的 issue tracker 上绘制一张**共享地图**，然后逐张处理其中的**决策工单**(解决后会得出决定的问题，而不是待执行的构建切片)，直到路线清晰。

每项工作的目的地各不相同，绘制地图的第一步就是为目的地命名：每张工单都由它来决定。目的地可能是要移交并迭代完善的规格说明、规划开始前必须确定的决定，或是在原位置发生的改动，例如数据结构迁移。地图不受领域限制：工程工作、课程内容，以及任何符合这种形态的工作都可以使用。

## 规划，不要执行

Wayfinder 默认用于**规划**：每张工单都要解决一项决定；当路径清晰、不再有任何决定需要在实际执行前作出时，地图就完成了。想直接开始实际工作，通常表示地图已经到达边界，该移交工作了。某项工作可以在其 **Notes** 中覆盖此默认行为，将执行工作纳入地图；如果没有这种覆盖，就应产出决定，而不是交付成果。

## 使用名称进行引用

每张地图和工单都是一个 issue，因此都有一个**名称**：它的标题。在人类阅读的所有内容中(讲述内容、地图中的 Decisions-so-far)，始终使用名称来引用它，不要只写编号、数字或缩写。一串 `#42, #43, #44` 难以阅读，名称一眼就能看懂。编号和 URL 仍然保留：名称会成为链接文本，将它们包含在名称之中，但编号和 URL 必须位于名称之中，不能取代名称。

## 地图

地图是本仓库 issue tracker 上的一个 issue，带有 `wayfinder:map` 标签，是规范记录。它的工单是作为地图子 issue 的 issue。

地图是**索引**，而不是内容存储处。它列出已经作出的决定，并指向记录详细内容的工单；一个决定只存放在一个地方，也就是对应工单，因此地图不会重述决定，只会概述并附上链接。

**地图、子工单、阻塞关系和前沿查询在 issue tracker 上的具体存放位置，由 issue tracker 决定。**issue tracker 配置应已提供给你。如果没有，告诉用户运行 `/setup-matt-pocock-skills`。参阅 issue tracker 文档中的"Wayfinding operations"章节，了解**本**仓库如何表达这些内容。如果尚未提供 issue tracker 配置，默认使用本地 Markdown issue tracker。

### 地图正文

每个会话只加载一次低分辨率地图，其中包含地图的全部内容。不会列出尚未关闭的工单：它们是尚未关闭的子 issue，应通过查询查找。

```markdown
## Destination

<到达地图终点的具体表现：规格说明、决定或此次工作旨在找出的变更。使用一两行；每个会话都要在选择工单前查看它，以了解目标。>

## Notes

<领域；每个会话都应查看的技能；针对这项工作的长期偏好>

## Decisions so far

<!-- 索引：每张已关闭工单占一行，提供足够信息来判断相关性，再点击链接查看工单中的详细信息 -->

- [<已关闭工单的标题>](link): <答案的一句话摘要>

## Not yet specified

<!-- 参阅"迷雾"：属于范围内但暂时还不能拆成工单的迷雾 -->

## Out of scope

<!-- 参阅"范围以外"：已经判断不属于目的地的工作；关闭后不会进入前沿 -->
```

### 工单

每张工单都是地图的**子 issue**，其身份由 issue tracker 中的 issue 编号决定。工单正文是问题，大小应适合一个 100K token 代理会话处理：

```markdown
## Question

<这张工单要解决的决定或调查问题>
```

每张工单都带有一个 `wayfinder:<type>` 标签，类型可以是 `research`、`prototype`、`grilling`、`task` 之一(参阅[工单类型](#ticket-types))。地图及其工单只能带有 `wayfinder:` 标签，不得附带 `ready-for-agent` 这类分流标签：这些是决策工单，不是实现工作。

会话应当先**认领**一张工单，再开始任何工作：将工单分配给负责推进地图的开发人员，让并发会话跳过该工单。分配对象**就是**认领者：尚未关闭且没有分配对象的工单尚未被认领。

阻塞关系使用 issue tracker 的**原生**依赖关系：这点至关重要，因为它能在 issue tracker 自己的界面中**直观显示**前沿，让人无需打开地图即可看到哪些工单可以开始处理。只有不支持原生阻塞关系的 issue tracker 才退回到正文约定。所有阻塞工单都关闭后，某工单才算**没有阻塞**；**前沿**是尚未关闭、没有阻塞且尚未认领的子工单，也就是已知范围的边界。

答案不属于工单正文；解决工单时才记录答案(参阅[处理地图](#work-through-the-map))。解决工单时创建的资源应链接到 issue，不要粘贴到正文中。

## 工单类型

每张工单都属于 **HITL**(人在循环中，由代理与代表自身表达意见的人共同处理)或 **AFK**(完全由代理处理)。HITL 工单只能通过当场互动解决；代理不能代替人表达其观点(负责深入追问的代理如果自行回答自己的问题，就没有完成工作)。

- **Research**(AFK)：阅读文档、第三方 API 或知识库等本地资源，找出某项决定所需的事实。由调用 Skill 工具并使用 "research" 的子代理解决。在需要获取当前工作目录之外的知识时使用。
- **Prototype**(HITL)：通过建立成本低、粗略但具体的成果(提纲、粗略方案、stub，或界面/逻辑代码)提高讨论的具体程度，让用户能够对此作出回应；调用 Skill 工具并使用 "prototype"。将原型作为资源链接。关键问题是"它应该是什么样子"或"它应该如何运作"时使用。
- **Grilling**(HITL)：对话。这是默认类型。始终调用 Skill 工具两次，分别使用 "grilling" 和 "domain-modeling"。
- **Task**(HITL 或 AFK)：在作出**决定**前必须完成的手动工作：没有问题需要决定、没有原型需要构建、也没有研究需要进行，但讨论会因此受阻。例如注册服务以便评估其 API、配置访问权限、迁移数据以便查看其形态。这是唯一一种会执行工作的类型；它的价值在于解除决策的阻碍，而不是交付目的地成果。代理可以独自完成时就自行处理(AFK)；否则向人提供准确的检查清单(HITL)。工作完成后即可解决工单；答案记录完成了什么以及后来工单所需的事实(凭据位置、新 URL、行数)。

## 战争迷雾

地图会**有意保持不完整**：还看不清的内容不要画入地图。尚未打开的工单之外是**战争迷雾**：你能判断某些决定和调查即将出现，但由于它们依赖仍未解决的问题，目前尚不能准确指定。解决工单后会驱散其前方的迷雾；随着前沿向前推进，已能具体描述的内容会逐项成为新工单，直到通往目的地的路径清晰，且没有工单剩余。

地图上的 **Not yet specified** 区块用于写下这种模糊的概况：可能存在的问题、以后需要重新查看的领域。它是通往目的地的未发现前沿：其中所有内容都在范围内，只是还没有明确到足以拆成工单。根据目前能看清的程度，尽量充分地写下内容；阅读地图的协作者也可以将其作为了解工作方向的路标。

**属于迷雾还是工单？**判断标准是：你现在能否精确描述这个问题，**而不是**你现在能否回答它。

- **如果**问题现在已经明确，即使它受阻，暂时不能开始处理，也应建立工单。
- **如果**你现在还无法把问题描述得足够明确，就应标记为 **Not yet specified**。不要预先将迷雾切成工单大小的片段：迷雾比工单粗略，一个片段随着前沿推进，最终可能变成好几张工单，也可能一张都不产生。

**Not yet specified** 不包含已经决定的事项(Decisions so far)、已经成为当前工单的事项，以及超出范围的事项(下一章节)。

## 范围以外

迷雾只会朝着目的地汇聚。目的地确定了工作范围，因此超出范围的工作属于**范围以外**：它不是迷雾，也不属于 **Not yet specified**。地图应有独立的 **Out of scope** 区块，记录你有意排除在**本次**工作之外的内容。是否超出范围由范围决定，不由问题是否清晰决定。

范围外的工作永远不会成为前沿的一部分(因为前沿在目的地处停止)，只有在重新确定目的地后，它才会以全新工作而非恢复原工作的形式重新出现。

将工作排除在范围之外是范围划定行为，不是路线中的一步。当一张已有工单被发现处于目的地之外(绘制地图时错误地将其纳入范围，或解决其他工单后发现不应处理)时，**关闭它**(关闭的工单明确不属于前沿)，并在 **Out of scope** 区块中写一行，说明其概要、范围外原因，并链接已关闭的工单。不要将它放入 **Decisions so far**：该区块只记录实际走过的路线；划定范围边界并不属于路线中的一步。

## 调用方式

有两种模式。无论采用哪种，**每个会话最多解决一张工单**，研究工单除外。

### 绘制地图

用户以一个宽泛想法调用技能。

1. **为目的地命名。**分别调用 Skill 工具两次，使用 "grilling" 和 "domain-modeling"，确定这张地图要找到什么：规格说明、决定或改动。目的地决定范围，所以先确定它。
2. **绘制前沿。**再进行一次深入访谈，这次使用**广度优先**的方式：展开覆盖整个领域，而不是在某个主题上深入挖掘，以便找出未解决的决定以及目前可以开始的第一步。**如果没有发现迷雾**(通往目的地的路径已经清晰，整个工作足够小，可以在一个会话内完成)，就无需制作地图。停止并询问用户接下来想怎么处理。
3. **创建地图**(标签为 `wayfinder:map`)：填写 Destination 和 Notes，保持 Decisions-so-far 为空，并在 **Not yet specified** 中勾勒迷雾。
4. 将当前可以明确描述的内容创建为地图的子 issue，然后在**第二遍**添加阻塞关系(必须先有 issue 编号才能互相引用)。也在这一步添加交叉引用，并使用真实编号：占位符 `#<n>` 会自动链接到不相关的 issue。添加关系后，工单会分别进入前沿或受阻状态；目前还不能明确描述的内容则保留在迷雾中，即 **Not yet specified** 区块。
5. **启动研究子代理。**为刚才创建的每张 `research` 工单启动一个子代理，让它调用 Skill 工具并使用 "research"，并行解决这些工单。将研究结果保存在临时的 `research/<name>` 分支上，并从工单添加上下文指针。推送分支，但不要创建 PR：该分支永远不会合并。
6. 停止：绘制地图是一个会话的工作；此阶段不会手动解决任何工单。

<a id="work-through-the-map"></a>

### 处理地图

用户通过地图(URL 或编号)调用技能。工单是**可选的**：用户没有指定工单时，由你选择下一项决定。

1. 加载**地图**：只加载低分辨率内容，不要加载每张工单的正文。
2. 选择工单。用户指定了工单时，就使用该工单；否则按顺序选择前沿中的第一张。**认领该工单**：开展任何工作前，先将它分配给自己。
3. 按照 `wayfinder:<type>` 标签所命名的类型解决工单(参阅[工单类型](#ticket-types))。阅读标签，不要只看正文：正文不会说明类型。**根据需要查看详情**：按需获取任何相关工单或已关闭工单的完整正文；调用 `## Notes` 区块中提及的技能。如有疑问，分别调用 Skill 工具两次，使用 "grilling" 和 "domain-modeling"。
4. 记录解决结果：发布一条**解决评论**作为答案，关闭 issue，并在地图的 Decisions-so-far 中**追加上下文指针**。
5. 添加新发现的工单(先创建再添加阻塞关系)；如果答案使某些迷雾内容变得明确，就将它们转为工单，并从 **Not yet specified** 中清除相应部分，使其只保留在新工单中。如果答案显示某张工单(当前工单或其他工单)位于目的地之外，就将它**划为范围外**，不要把它作为路线中的决定来解决。如果某个决定使地图上的其他内容失效，就更新或删除相应工单。

用户可能会并行处理没有阻塞的工单，因此应预期其他会话也会同时编辑 issue tracker。
