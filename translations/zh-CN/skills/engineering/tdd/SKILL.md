# 测试驱动开发

测试驱动开发是红色 → 绿色的循环。此技能是参考指南，确保循环产出的测试值得保留：说明好测试的特点、测试应放在哪里、反模式和循环规则。每个循环都适用所有章节：循环前和循环期间都要查阅，而不是结束后才看。

探索代码库时，如果存在 `GLOSSARY.md`，请阅读它，使测试名称和接口词汇符合项目领域语言。阅读相关区域当前有效的 OpenSpec 规格和已确认决定，必要时检查相关归档变更。提案不等于已确认的决定。

## 好测试的特点

测试通过公开接口验证行为，而不是验证实现细节。代码可以完全改变，测试却不应该改变。好测试读起来像规格说明："用户可以使用有效购物车结账"能明确告诉你存在什么能力，而且由于它不关心内部结构，所以能经受重构。

查看 [tests.md](tests.md) 了解示例，并查看 [mocking.md](mocking.md) 了解模拟指南。

## 接缝：测试应放在哪里

**接缝**是你进行测试的公开边界：可以在不深入内部的情况下观察行为的接口。测试应放在接缝处，绝不能直接针对内部实现。

**只在事先约定的接缝处测试。** 编写任何测试之前，先写下要测试的接缝，并与用户确认。未经确认的接缝不得编写测试。你不可能测试所有内容，因此提前约定接缝，可以让测试投入到关键路径和复杂逻辑上，而不是覆盖每个边缘情况。

询问："公开接口是什么？我们应该测试哪些接缝？"对每个建议的接缝，用一句话说明它能发现什么，不能发现什么。

如果接口形态本身存在疑问(模块有多深、接缝应该在哪里、接口应该公开什么)，则调用 Skill 工具并使用 `codebase-design` 获取相关词汇。该技能提供模块、接口、深度、接缝、适配器、调用方收益和局部集中度的共用词汇，是供参考的资料，而不是要启动的一场会话。

## 反模式

- **与实现耦合**：模拟内部协作者、测试私有方法，或通过旁路验证(例如查询数据库，而不是使用接口)。判断方法：重构后行为没有变化，测试却会失败。
- **同义反复**：断言按照代码的计算方式重新计算预期值(`expect(add(a, b)).toBe(a + b)`、手工按相同方式生成的快照，或断言常量等于自身)，因此测试必然通过，不可能与代码结果不一致。预期值必须来自独立事实依据：正确的字面值、计算示例或规格说明。
- **横向切片**：先写完所有测试，再编写实现。批量测试验证的是_想象中的_行为：测试的是形状而非面向用户的行为，且对真实更改不敏感；你还未理解实现就承诺了测试结构。应采用**纵向切片**：一次一个测试 → 一次一个实现，逐个重复；每个测试都是一颗**曳光弹**，根据上一个循环得到的信息来调整。

## 循环规则

- **先红后绿。** 先编写失败测试，然后只写足以让它通过的代码。不要预想未来的测试，也不要添加推测性功能。
- **一次一个切片。** 每个循环只处理一个接缝、一个测试和一个最小实现。
- **重构不属于循环。** 重构属于审查阶段(参见 `code-review` 技能)，不属于红绿实现循环。
