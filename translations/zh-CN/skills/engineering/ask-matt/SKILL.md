# Ask Matt

你不必记住所有技能，所以可以提问。

在说明某项技能的作用或建议跳过某个步骤之前，先阅读该技能的 SKILL.md：这里的摘要只用于了解方向。

**工作流程**是技能之间的一条路径。大多数路径沿着一条**主流程**进行，并有两条汇入主流程的**入口**。其他技能都是独立技能，或是从下方支撑流程的词汇参考层。

## 主流程：从想法到发布

大多数工作都会沿着这条路径进行。你有一个想法，希望把它构建出来。

1. **`/grill-with-docs`** 通过访谈打磨想法。只要**正在某个工作目录中工作**，就从这里开始：它会保存并持续补充所学内容到 `GLOSSARY.md` 和 ADR 中。（没有工作目录？请使用 `/grill-me`，它在“独立技能”部分介绍。两者使用相同的 `/grilling` 基本流程；`grill-with-docs` 会留下记录，因此只要存在可保存记录的仓库，它就是更好的选择。）

2. **分支：能否在对话中解决所有问题？**如果某个问题需要可运行的答案（状态、业务逻辑，或必须亲眼查看的界面），就转去做原型，两个方向都通过 **`/handoff`** 连接（原型有自己的目录，正好适合使用 `/handoff`；请参阅“阶段边界”）：
   - 使用 `/handoff` 转出，然后在该文件上开启一个新会话，
   - 使用 `/prototype` 通过临时代码回答问题，
   - 使用 `/handoff` 移交学到的内容，并在原始想法会话中引用它。

3. **分支：这是一个需要多个会话完成的构建吗？**
   - **是** → 使用 `/to-spec`（将当前对话整理为规格说明），然后使用 `/to-tickets` 将规格拆分为曳光弹（tracer bullet）工单，并在每张工单上声明其**阻塞关系**。之后有两种方式处理工单：
     - 每张工单使用一次 **`/implement`**，并在每张工单之间使用 **`/clear`** 清空上下文。本地议题跟踪系统中，每张工单对应 `.scratch/<feature>/issues/` 下的一个文件，按阻塞关系由前到后手动处理；真实议题跟踪系统中，阻塞关系会成为原生链接，因此阻塞项都已完成的工单均可领取。每张工单自成一体，所以最后一张工单所处的上下文可以丢弃。
     - 使用 **`/implement-spec`** 一次处理完整规格说明。它会把工单作为**任务图**读取，在准备就绪的**前沿**上并行运行实现子代理，并将所有工作汇入同一个**集成分支**。如果你更愿意协调整个构建，而不是亲自逐张推进工单，就使用它。
   - **否** → 立即在同一上下文窗口中使用 `/implement`。

   无论采用哪种方式，都要通过执行 `/tdd` 构建代码（一次处理一个红绿切片），并以 `/code-review` 收尾。`/implement` 会针对每张工单分别运行两者；`/implement-spec` 的实现人员各自执行 `/tdd`，并对集成分支执行一次 `/code-review`。它会从两个角度审查差异：**Standards**（是否遵循编码标准）和 **Spec**（是否忠实实现了原始问题/规格说明）。只想先写测试再构建具体行为时，单独使用 `/tdd`；想根据固定基准点审查分支或 PR 时，单独使用 `/code-review`。

   工作以拉取请求提交时，使用 `/pr` 编写正文：用最小的图示说清改动，用前后证据证明它可用，并判断合并危险程度（单向门或双向门，以及影响范围）。它由模型调用，因此代理在撰写 PR 时会使用它。

4. **`/retro`** 结束整个循环。它会在构建之后回顾会话，尤其适用于工作出错的情况，并建议改进代理的**运行环境**，而不是代码：导航指引、自动检查、`/code-review` 执行的编码标准、引导文件、工具。机械性错误应转换为确定性检查；需要判断的内容则转换为编码标准。这样，下一次构建就会从更好的运行环境开始。

### 上下文管理

步骤 1 到 3 应在**一个不中断的上下文窗口**中完成（直到 `/to-tickets` 之后都不要压缩或清空），这样深入追问、规格说明和工单就会建立在同一套思考上。每次 `/implement` 都从新上下文开始，依据工单开展工作。应在正在回顾的会话中运行 `/retro`，并在清空上下文前运行；清空后则将该会话的日志交给它。

此要求受限于**[智能区（smart zone）](https://www.aihero.dev/ai-coding-dictionary/smart-zone)**：在其中（当今先进模型约有 150k tokens），模型仍能清晰推理。如果会话在运行 `/to-tickets` 前接近这个范围，不要在推理能力下降时硬撑；请在最近的阶段边界使用 `/compact`，然后继续（参阅“阶段边界”）。

## 工作入口

从某种情形开始，产生工作后再汇入主流程。

- **错误和请求不断累积** → 使用 `/triage`。它会让问题经过分流角色处理，并生成可交给代理处理的问题，之后由 `/implement` 接手。

  只对**并非由你创建**的问题使用分流：错误报告、收到的功能请求，以及任何原始提交的问题。`/to-tickets` 生成的工单已经可以交给代理处理，因此**不要对它们进行分流**。

- **出现故障** → 使用 `/diagnosing-bugs`。适用于难以排查的问题：乍看之下找不到原因的错误、间歇性问题，以及两个已知正常状态之间引入的回归。它要求先建立一个**紧密反馈循环**（运行一个针对该错误且已经失败的命令），然后才提出理论，并使用回归测试修复问题。完成修复后，在同一会话中运行 `/retro`，询问怎样才能预防这个错误；如果真正的问题是缺少能锁定行为的良好接缝，那就交给 `/improve-codebase-architecture` 处理。

- **规模庞大、方向模糊的工作：从零开始的项目或大型功能构建，超出单一会话的承载范围** → 使用 `/wayfinder`，这是此处认知要求最高的流程。如果还看不清从当前位置到目的地的路径，它会在议题跟踪系统上绘制一张**共享地图**，包含一系列**决策工单**，再逐张解决，直到迷雾散去。它会产出的是**决策，而不是交付成果**。如果想法能在一个会话中掌握，应使用 `/grill-with-docs` 来打磨；wayfinder 适用于无法在单一会话中掌握的想法，过程更慢、更密集，只在确有此需要时使用，绝不要用于范围明确的功能。

  地图清晰后，**它会移交工作，而不会开始构建**：使用 `/to-spec` 汇入主流程，将地图上相关联的决定归纳成可构建的计划，然后像往常一样使用 `/to-tickets` 和 `/implement`。直接从地图进入 `/implement` 会跳过归纳步骤并丢失关联细节，因此只有在确认工作实际很小时才能直接进入 `/implement`。

## 代码库维护

不是功能开发，而是维护工作。

- 有空时可以运行 `/improve-codebase-architecture`，让代理更容易在代码库中工作。它会找出**加深模块的机会**；选中某项机会就会**产生一个想法**，你可以使用 `/grill-with-docs` 将其带入主流程。它负责调查并发现候选机会；下方的 **`/codebase-design`** 是用来设计所选机会的工作台。

## 下层词汇

两项由模型调用的参考技能会从下方支撑其他技能；每项都是其词汇范围内的唯一可信来源。当问题在于**用词**而非流程时，可以直接使用它们，也可以让上述技能调用它们。

- **`/domain-modeling`**：打磨项目的*领域*用语：质疑模糊术语，解决多义词（例如“account”同时承担三种含义），并将难以撤销的决定记录为 ADR。它是 `/grill-with-docs` 使用的主动实践，用于保持 `GLOSSARY.md` 作为整洁的术语表。
- **`/codebase-design`**：用于设计模块*形状*的深模块词汇（模块、接口、深度、接缝、适配器、调用方收益（leverage）、局部集中度（locality））：在干净的接缝处，通过小型接口承载大量行为。`/tdd` 和 `/improve-codebase-architecture` 都使用这些词汇。

## 阶段边界

一个**阶段**是一次会话中的一段工作，如深入追问、实现、质量保证。两个阶段之间有五种选择，而在这张地图中的所有决定里，这是最模糊的一项：

- **Continue**：留在当前会话中，既不耗费资源，也不会丢失内容。
- **`/clear`**：清空窗口，适用于当前内容与下一步无关的情况。
- **`/handoff`**：编写可移植的 Markdown 文件。仅在切换到**新运行环境**、**新目录**、移交给**同事**，或在**阶段中途**拆分旁支任务时使用。它提供可移植性。
- **Subagent**：将范围明确的任务交给自己的上下文窗口，并取得报告。
- **`/compact`**：压缩当前上下文并以此开始新会话。它是默认选择，处于判断路径的末尾，不是优先选择。

阅读 [PHASE-BOUNDARIES.md](PHASE-BOUNDARIES.md)，了解依序判断的路径：五个问题、每个分支背后的理由，以及为何应先判断能否 **Continue**（继续），再考虑其他方式：选择其他方式会使一手资料转换为二手资料并造成信息损失。应在阶段边界处作决定；阶段进行中，继续工作或将剩余工作拆分给子代理。

## 独立技能

完全脱离主流程。

- **`/grill-me`**：与 `/grill-with-docs` 一样持续追问，但它是**无状态的**：不在本地保存任何内容，也不会创建 `GLOSSARY.md`。当你**不在某个工作目录中**（打磨计划、设计、文章，或其他没有仓库的内容）时使用。如果你正在工作目录中，应改用 `/grill-with-docs`：它执行相同的访谈并留下记录，因此它显然更好。
- **`/grilling`**：访谈的基本流程本身：按轮次展开，代理负责确定前沿，事实是代理的工作，决定则由你作出。`/grill-me` 和 `/grill-with-docs` 是两个有名称的入口；`/triage`、`/wayfinder` 和 `/improve-codebase-architecture` 内部也会运行它。只有在你需要直接使用访谈且不需要任何外层包装时，才直接调用它。
- **`/prototype`**：回答一个设计问题的小型临时程序：例如状态模型是否合适，或界面应该是什么样子。“临时”限制的是代码编写方式，不代表必须销毁它：答案会合并到真实代码中，原型本身会作为**一手资料**保存在从 main 分支创建的 `prototype/<name>` 分支上，并由实现问题指向。它是主流程步骤 2 的旁支，但任何难以通过讨论决定的设计问题都可以使用它。
- **`/research`**：将阅读调查工作交给**后台代理**：该代理针对**一手资料**调查问题，并在仓库中留下一份附带引用的 Markdown 文件。让它调查时，你可以继续工作。该文件可带入主流程的 `/grill-with-docs`，因为研究的作用是提供思考材料，而不是取代思考。
- **`/to-questionnaire`**：当阻碍不在你的想法或代码库中，而在**其他人的想法里**时使用。它会编写一份供他人填写的问卷。它与 `/grill-me` 正好相反：不是访谈你对主题的理解，而是访谈你关于**发送问卷**的情况（问卷会发给谁、需要对方回复什么），再围绕信息缺口设计问题。收到的回复可以交给 `/grill-with-docs` 或 `/to-spec`。
- **`/wizard`**：处理只有**人**才能完成的步骤：配置基础设施、设置凭据或持续集成机密、操作不熟悉的第三方仪表板，或执行一次性迁移、切换。它会生成一个交互式 bash 脚本，打开每个 URL、收集每项值，并将其写入 `.env` 和 GitHub secrets，这样代理就不用每次都重新解释整个流程。它由模型调用，因此代理一遇到只有你能克服的阻碍就会使用它。如果代理可以自行完成，就应该自行完成；只有真正需要人参与的步骤才使用它。
- **`/wait-what`**：用于纠正对方没有理解的信息。在任何对话期间、任何其他技能内部都可以使用，让代理根据你缺少的上下文，用通俗英语并使用 `GLOSSARY.md` 中的词汇重新表达刚才的内容。它是在事后纠正；`/grill-with-docs` 则是事前的解决办法，因为及早达成共同语言才能避免术语一开始就没有被理解。
- **`/teach`**：使用当前目录作为有状态的工作区，跨多个会话学习某个概念。
- **`/writing-for-agents`**：为代理撰写文档的参考，适用于技能、AGENTS.md 和被其他文档引用的文档。

## 前置条件

**`/setup-matt-pocock-skills`**：首次使用任何工程流程前运行，用于配置议题跟踪系统、分流标签以及领域文档布局，供其他技能使用。也可以使用自定义议题跟踪系统。
