# 改进代码库架构

揭示架构中的摩擦，并提出**加深模块的机会**：将浅层模块转变为深层模块的重构。目标是让代码更便于测试和供 AI 导航。

此命令根据项目领域模型提供的信息进行分析，并使用共用的设计词汇：

- 调用 Skill 工具并使用 `codebase-design`，获取架构词汇（**模块**、**接口**、**深度**、**接缝**、**适配器**、**调用方收益**、**局部集中度**）及其原则（删除模块检验、“接口就是测试面”、“一个适配器代表假设中的接缝，两个才代表真实接缝”）。每条建议都要准确使用这些术语，不要偏离到“组件”、“服务”、“API”或“边界”等词语。
- `GLOSSARY.md` 中的领域语言为合适的接缝命名；`docs/adr/` 中的 ADR 记录了此命令不应重新讨论的决策。

## 流程

### 1. 探索

**扫描之前先确定范围：YAGNI。** 加深模块的价值在于让未来更容易修改该模块，因此要特别关注最近有过更改的代码库部分。确定先看哪里，然后再开始查看：

- 如果用户指出了方向（模块、子系统、痛点），就按用户指定的方向进行，并跳过以下推断过程。
- 否则，回溯一段较长的提交历史（`git log --oneline`），找出代码库中的热点，即反复修改的文件和区域，优先关注这些路径。如果更改分散，没有明显热点，就扩大搜索范围。

先阅读项目领域词汇表（`GLOSSARY.md`）和相关区域中的任何 ADR。

然后启动一个子代理检查代码库。不要拘泥于固定启发式；应自然探索，并记录遇到摩擦的地方：

- 理解一个概念是否需要在许多小型模块之间来回跳转？
- 是否存在**浅层**模块，其接口几乎和实现一样复杂？
- 是否仅为便于测试而提取了纯函数，但真正的错误隐藏在调用方式中（缺乏**局部集中度**）？
- 紧密耦合的模块是否跨接缝泄漏？
- 代码库中哪些部分没有测试，或难以通过现有接口进行测试？

对任何疑似浅层模块都进行**删除模块检验**：删除它会让复杂性集中起来，还是只会将复杂性转移到别处？如果答案是“会集中”，这就是你要找的信号。

### 2. 将候选项制作为 HTML 报告

将独立 HTML 文件写入操作系统临时目录，不要在仓库中留下任何文件。根据 `$TMPDIR` 确定临时目录；如果没有设置，则使用 `/tmp`（Windows 使用 `%TEMP%`）；写入 `<tmpdir>/architecture-review-<timestamp>.html`，确保每次运行都生成新文件。为用户打开文件（Linux 使用 `xdg-open <path>`，macOS 使用 `open <path>`，Windows 使用 `start <path>`），并告知用户绝对路径。

报告使用 **Tailwind CDN** 进行布局和样式设置，在图形、流程或顺序能够清晰表达结构时使用 **Mermaid CDN**。Mermaid 与手工编写的 CSS/SVG 图示混合使用：关系呈图形结构（调用图、依赖关系、顺序）时使用 Mermaid；想要更具编辑风格的图示（体量图、剖面图、折叠动画）时使用手工制作的 div/SVG。不要凡事都依靠 Mermaid，否则报告会显得千篇一律。每个候选项都应有**修改前 / 修改后图示**。视觉呈现应充分。

对于每个候选项，呈现一张卡片，其中包含：

- **文件**：涉及哪些文件或模块。
- **问题**：当前架构为何造成摩擦。
- **解决方案**：用简单英语说明需要更改什么。
- **收益**：从局部集中度和调用方收益角度说明，并说明测试将如何改进。
- **修改前 / 修改后图示**：并排显示自定义图示，说明浅层状态和加深后的状态。
- **建议强度**：使用 `Strong`、`Worth exploring`、`Speculative` 之一，渲染为徽章。

报告最后附上**首要建议**章节，说明应优先处理哪个候选项及理由。

**领域语言使用 GLOSSARY.md 中的词汇，架构语言使用 `/codebase-design` 中的词汇。** 如果 `GLOSSARY.md` 定义了 “Order”，就说“Order 接收模块”，不要称作“FooBarHandler”，也不要称作“Order 服务”。

**与 ADR 冲突时**：如果候选项与现有 ADR 冲突，只有当摩擦严重到足以重新审议 ADR 时才展示它。要在卡片中明确标记（例如警告框：“与 ADR-0007 冲突，但因为……值得重新审议。”）。不要列出 ADR 禁止的所有理论性重构。

参见 [HTML-REPORT.md](HTML-REPORT.md)，了解完整 HTML 框架、图示模式和样式指引。

暂时不要提出接口。文件写好后，询问用户：“你想深入讨论哪一项？”

### 3. 深入讨论循环

用户选定候选项后，调用 Skill 工具并使用 `grilling`，与用户一起逐步梳理决策：约束、依赖、加深后的模块形态、接缝后放置的内容，以及哪些测试应当保留。

随着讨论逐渐形成决策，副作用应同步处理；调用 Skill 工具并使用 `domain-modeling`，及时更新领域模型：

- **加深后的模块名称使用了 `GLOSSARY.md` 中没有的概念？** 将术语添加到 `GLOSSARY.md`。如果文件不存在，则在需要时创建。
- **讨论期间明确了含糊术语？** 当场更新 `GLOSSARY.md`。
- **用户因重要理由拒绝候选项？** 提议记录为 ADR，措辞如下：“你想把这个决定记录为 ADR，以免未来的架构审查再次推荐它吗？”只有当未来探索人员确实需要该理由，才能避免重复建议时才提出；短期理由（例如“现在不值得做”）或显而易见的理由则跳过。
- **想探索加深后模块的其他接口？** 调用 Skill 工具并使用 `codebase-design`，采用其中的“双重设计”并行子代理模式。
