## 功能说明

`implement-spec` 接收一份[规格说明](https://www.aihero.dev/ai-coding-dictionary/spec)及其[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)，并在一次运行中完成全部工作。负责协调的[代理](https://www.aihero.dev/ai-coding-dictionary/agent)会将每个工单交给实施[子代理](https://www.aihero.dev/ai-coding-dictionary/subagent)，每个子代理都在自己的 git worktree 中工作；协调代理将每个完成的分支合并到同一个**集成分支**，对结果运行 [code-review](https://aihero.dev/skills-code-review)，并解决工单。

它将工单视为**任务图**，而不是列表。依赖边决定哪些工单可以开始，因此任意时刻都有一组依赖项已全部合并的**前沿工单**，前沿中的每个工单都会同时运行。这就是它与逐个处理工单的不同之处。任务图的结构决定进度，而不是跟踪系统中的工单排序。

## 适用情形

输入 `/implement-spec` 调用此技能；代理不会自行调用。

| 你的情况 | 使用方式 |
|---|---|
| 一份规格说明已拆分成具有依赖关系的工单，希望一次完成 | `/implement-spec` |
| 一次处理一个工单，在自己的[上下文窗口](https://www.aihero.dev/ai-coding-dictionary/context-window)中完成，并在工单之间[清理上下文](https://www.aihero.dev/ai-coding-dictionary/clearing) | [implement](https://aihero.dev/skills-implement) |
| 规格说明还没有拆分成工单 | 先使用 [to-tickets](https://aihero.dev/skills-to-tickets) |
| 工作量很小，没有真正的任务图 | 直接使用 [implement](https://aihero.dev/skills-implement) |

## 前置条件

- **议题跟踪系统。** 此技能会从 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 配置的跟踪系统中读取工单，并在其中解决工单。如果尚未配置，技能会停止并告知你先运行配置流程，而不会猜测。
- **带有依赖关系的工单**，由 [to-tickets](https://aihero.dev/skills-to-tickets) 按此方式编写。没有依赖边时，任务图就是平面图，所有工单会同时开始。
- **能够在后台运行子代理并为每个子代理提供 git worktree 的[运行环境](https://www.aihero.dev/ai-coding-dictionary/harness)。** 此技能的目的就是同时处理工单，因此，如果运行环境只能逐个运行子代理，它就只是速度更慢的 `implement`。

## 集成分支

所有更改都合并到一个分支。每个实施代理都要：

1. 在开始前确认自己的 worktree 基于集成分支。
2. 使用 [tdd](https://aihero.dev/skills-tdd) 实现工单，一次一个红绿切片。
3. 报告完成前，将集成分支最新提交合并到自己的分支，以便后续直接快进合并。

是否创建拉取请求由跟踪系统决定。如果跟踪系统通过 PR 关闭工作，或你要求创建 PR，则技能会在第一次合并后打开草稿 PR，并在最后标记为准备审查。否则，运行会停在集成分支上，并按照跟踪系统的方式解决所有工单；对本地 Markdown 跟踪系统而言，这种工作方式完全可以脱机运行。

实施代理通过[上下文指针](https://www.aihero.dev/ai-coding-dictionary/context-pointer)(指向规格说明、工单、共享探索笔记、早期提交)而不是粘贴摘要，与协调代理沟通。这样每个子代理的提示都很小，也为协调代理的上下文窗口保留了处理任务图的空间。

## 常见问题

**这和我自行对每个工单运行 `/implement` 有什么不同？**

这正是此技能要回答的问题。发布之前，人们一直在构建自己的版本。一位用户描述了需求：希望"让子代理实现工单"，而不是"必须逐个创建新会话并要求它们实现工单，因为一份规格说明可能有五个以上工单"。使用 `implement` 时，你负责分派工作：每个工单一个[会话](https://www.aihero.dev/ai-coding-dictionary/session)，在工单之间清理上下文，并自行跟踪哪些工单已经解除阻塞。`implement-spec` 则将这一任务交给一个协调会话。代价是，你不会在每个工单合并时逐一阅读其工作；而是在最后审查集成分支。要开始运行，请清理上下文，然后输入 `/implement-spec` 并提供规格说明指针(议题编号或文件路径)。工作量较小且没有真正任务图时，跳过此技能，直接使用 `implement`。

**必须使用 GitHub 吗？我希望它停在分支上。**

不再需要了。一位喜欢测试阶段版本的用户曾提出这个问题："它最后会创建 PR，这就需要 GitHub 这样的在线仓库。我希望它也能脱机完成同样的工作，并停在所有更改已经合并的分支上。"现在运行会停在集成分支上。只有当已配置的跟踪系统通过 PR 关闭工作，或你要求创建 PR 时，才会打开 PR；因此对于本地 Markdown 跟踪系统，运行会以全部工单已解决、所有工作已合并到该分支的状态结束。

**审查和修复循环运行了几个小时，或持续"修复"尚未实现的工单。**

如果 `code-review` 在此技能指定的时间点以外运行，就可能发生这两种情况。它会按照完整规格说明检查代码，因此只有所有工单都已合并后才有意义。如果运行中途执行审查，所有尚未实现的工单都会被判定为失败。代理接着实现该工单，又会触发新一轮审查。最终技能会运行一次 `code-review`，并将所有发现交给一个修复子代理，但尚未说明修复后何时停止。一位用户报告，一个五工单功能的"审查和修复循环耗时大约四小时"。如果你看到第二轮全面审查开始，请要求它针对已修复的问题运行重点检查，然后停止。首次审查应会发现真实问题。运行结果是待审查的草稿，由审查补全，不应直接发布。

**它像 `implement` 一样驱动 TDD 吗？**

现在会，最初并不会。用户在测试阶段版本中发现"实施子代理没有继承 `/tdd` 指令"，因此从单个工单扩展到完整规格说明时，红绿流程就停止了。现在每个实施代理都会使用 `tdd` 实现自己的工单。不过，此技能没有 `implement` 会话中的交互环节来约定接缝，因此如果希望明确指定接缝，就应在规格说明或工单中写出接缝名称。

**两个实施代理并行运行时修改了同一个文件，或给同一事物起了不同名字。**

worktree 不会消除冲突，只会将冲突推迟到合并阶段。根据工单文字编写依赖边，只能猜测每个工单会修改哪些文件；即使两个工单涉及"代码库的不同部分"，它们仍可能共享消息目录、配置注册表或类型。每个实施代理只能看到自己的工单和共享笔记，看不到其他代理的进行中工作。因此，某位用户的网页和移动端工单分别新增了名为 `blockedSince` 和 `blockedOn` 的同一字符串。当两个前沿工单会修改同一个共享文件时，可以在它们之间增加依赖边，让它们按顺序执行；也可以让探索笔记明确规定每个工单应新增的准确名称。

**阻塞工单在阻塞它们的工单合并后仍未启动。**

这是 GitHub 上已知的问题。只有阻塞工单**关闭**后，跟踪系统的阻塞计数才会下降；而工单通常要等 PR 合并后才会关闭，这已经是运行结束时了。跟踪系统是获取初始任务图的正确来源，但运行过程中可能已经过时。让协调代理自行跟踪哪些工单已经合并到集成分支，并据此计算前沿。

**这会取代 Sandcastle 或无人值守脚本吗？**

不会。有人会这样问，因为技能现在可以处理实现："Sandcastle 还有用吗？你的技能现在好像也可以实现内容了。"`implement-spec` 在单个运行环境会话中指挥代理进行协调，无需基础设施，且你可以观察并引导。如果工作确实是[无人值守](https://www.aihero.dev/ai-coding-dictionary/afk)的，确定性循环([Sandcastle](https://github.com/mattpocock/sandcastle)、Shell 脚本、CI 作业)更快、更便宜、更可靠，因为没有代理参与协调决策。

**某项关键测试在工单的 worktree 中被跳过，但工单却报告通过。**

worktree 只包含 Git 跟踪的内容。读取 Git 忽略的夹具、本地数据库或凭据的测试，可能会在其中静默跳过。如果工单的验证依赖未跟踪内容，请让协调代理改在主检出目录中运行它。

## 判断是否有效

- 任务图允许时，多个实施代理会同时运行，而不是一个接一个运行。
- 某工单最后一个阻塞项合并到集成分支后，它就会立即开始，而不是等到整个运行结束。
- 每个工单的运行记录都显示已运行 `tdd`，并且在代码之前运行了失败测试。
- 合并到集成分支时采用快进合并，而不是解决冲突。
- 运行结束时只留下一个分支，所有工单都已解决；只有跟踪系统要求时才创建 PR。

## 它在工作流程中的位置

`implement-spec` 是主要流程链的构建步骤，是每个工单单独运行一次 [implement](https://aihero.dev/skills-implement) 的并行替代方案：

```txt
grill-with-docs → to-spec → to-tickets → implement-spec → retro
```

相邻技能包括 [to-tickets](https://aihero.dev/skills-to-tickets)，它会记录此技能用作任务图的依赖边；以及 [code-review](https://aihero.dev/skills-code-review)，它会在结束工作前审查集成分支。如果不确定自己应使用哪种流程，[ask-matt](https://aihero.dev/skills-ask-matt) 会在整组技能中进行引导。
