## 功能说明

`code-review` 从两个方面审查你指定的固定参照点(提交、分支、标签、`main`、`HEAD~5`)与 `HEAD` 之间的差异。**编码标准(Standards)**检查代码是否遵循本仓库的编码方式。**规格说明(Spec)**检查代码是否符合发起此工作的议题或[规格说明](https://www.aihero.dev/ai-coding-dictionary/spec)要求。两个方面分别由独立的[子代理](https://www.aihero.dev/ai-coding-dictionary/subagent)执行，因此彼此看不到对方的推理。

此技能绝不合并或重新排序两个维度的审查发现。报告结尾会分别列出两个维度各自最严重的问题，而不会强行给出一个单一总评或综合裁决。一项更改完全可以在一个维度通过，在另一个维度失败。遵循所有编码规范却实现了错误业务逻辑的代码，在"标准"维度通过，在"规格说明"维度失败；完全符合[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)要求却严重破坏代码规范的改动则正好相反。混合评定只会让通过的维度掩盖真正失败的维度。

## 适用情形

输入 `/code-review`，或者当你要求审查某个分支、PR、进行中的工作，或"自 X 以来"的任何更改时，代理会自动使用此技能。

| 你的情况 | 使用方式 |
| --- | --- |
| 已有差异，你想知道实现是否正确，且做的是否是正确的事情 | `code-review` |
| 你想从差异中查找错误：空值路径、竞态、偏一错误 | 使用 Claude Code 自带的代码审查，而不是此技能(见下方名称冲突) |
| 尚未编写代码，并希望先写测试再实现 | [tdd](https://aihero.dev/skills-tdd) |
| 需要实现完整规格说明，并包含审查 | [implement](https://aihero.dev/skills-implement)，它会自行调用此技能 |
| 整个代码库都发生偏离，而不只是一个差异 | [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) |
| 某项功能损坏，但你不知道原因 | [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs) |

你必须提供固定参照点。如果没有提供，此技能会要求你提供，而不会自行猜测。启动任何子代理之前，技能会检查引用是否有效以及差异是否非空，因此分支名称输错时，会在你面前报错，而不是等到两个子代理内部才出错。

## 前置条件

编码标准(Standards)方面没有前置条件。它会读取仓库记录的标准(例如 `CODING_STANDARDS.md`、`CONTRIBUTING.md`)，如果仓库没有记录，则使用内置基准。

规格说明方面需要存在且能够找到规格说明。它按以下顺序查找：

1. 提交说明中的议题引用(`#123`、`Closes #45`、GitLab `!67`)，通过跟踪系统文档获取。
2. 你作为参数传入的路径。
3. `docs/`、`specs/` 或 `.scratch/` 下与分支或功能名称相符的规格说明文件。
4. 询问你。

步骤 1 依赖跟踪系统文档，该文档由 [setup-matt-pocock-skills](https://aihero.dev/skills-setup-matt-pocock-skills) 编写。没有该文档时，如果你提供路径，此方面仍可运行。如果完全没有规格说明，技能会跳过规格说明子代理，并在报告中写明"没有可用规格说明"，不会凭空编造要求。

## 两个审查方面

| | 编码标准(Standards) | 规格说明(Spec) |
| --- | --- | --- |
| 问题 | 实现是否正确？ | 是否做了正确的事情？ |
| 阅读内容 | 仓库记录的标准，以及代码异味基准 | 发起工作的议题或规格说明 |
| 报告内容 | 记录的违规(可能属于硬性违规)和代码异味(始终需要判断) | 缺失或不完整的要求、范围扩大、实现错误的要求 |
| 每项发现都引用 | 标准文件和具体规则，或代码异味名称及代码片段 | 规格说明中的对应行 |

此设计用于避免通用审查技能不了解你们的编码标准。这类技能可能会指出代码库有意采用的做法，却漏掉代码库依赖的不变量。因此，在编码标准(Standards)方面，仓库自身文档是[一手资料](https://www.aihero.dev/ai-coding-dictionary/primary-source)，而且**仓库标准始终优先**。

**代码异味基准**属于仓库标准的补充内容。它取自 Fowler《重构》第 3 章，共包含十二种代码异味：神秘名称 (Mysterious Name)、重复代码 (Duplicated Code)、特性依恋 (Feature Envy)、数据团簇 (Data Clumps)、基本类型偏执 (Primitive Obsession)、重复分支判断 (Repeated Switches)、霰弹式修改 (Shotgun Surgery)、发散式修改 (Divergent Change)、推测式通用性 (Speculative Generality)、消息链 (Message Chains)、中间人 (Middle Man)、被拒绝的遗赠 (Refused Bequest)。每种都是带标签的启发式判断("可能存在 Feature Envy")，绝不是硬性违规。每种异味都说明问题及修复方式，因此发现中包含修复建议，而不是只有抱怨。两个方面都跳过代码检查器已经强制执行的内容。

## 常见问题

**它与 Claude Code 自带的 `/code-review` 冲突，该怎么办？**

这是此技能最常被报告的问题，目前尚未解决。Claude Code 自带 `/code-review`，作用不同：它在代码差异中排查代码缺陷，而本技能检查规格说明符合度与仓库编码规范。安装此技能库时，两者会产生优先级覆盖，具体取决于安装方式：

- **插件市场安装。** 每个技能名称都会加上 `mattpocock-skills:` 前缀，因此不带前缀的名称很难访问内置技能。
- **普通技能安装。** 以本地文件优先，此技能会遮蔽内置技能。

一种做法是完全移除 Claude Code 内置技能。这会节省大量[上下文](https://www.aihero.dev/ai-coding-dictionary/context)，也会消除名称冲突。遮蔽本身可以视为 Claude Code 的[运行环境](https://www.aihero.dev/ai-coding-dictionary/harness)错误(技能作者应当可以随意命名技能)，所以另一种做法是重命名本地副本。`npx skills update` 会撤销对前置元数据的编辑，或撤销重命名目录的操作。用户报告的持久解决办法是将技能分支为新名称，并从受管理的技能集合中移除 `code-review`。记下分支来源提交，以便之后手动同步。

**它的子代理会再次调用 `/code-review`，并继续启动更多代理。**

这是已知且尚未解决的问题。已有几个人在多个运行环境中复现。标准和规格说明提示没有禁止委派，因此子代理可能再次找到此技能并继续扩散。曾有报告称代理数量超过 50 个。用户在分支版本中采用的修复方式是在两个子代理说明末尾加上一行："不要调用 `/code-review`，也不要启动其他代理；直接执行审查。"有些人更愿意在运行环境层面处理，使所有技能都继承此限制。目前发布的技能中还没有任何一种解决办法。如果无人值守运行，请留意代理数量。

**我应该在编写代码的同一[会话](https://www.aihero.dev/ai-coding-dictionary/session)中运行它吗？**

建议使用新会话。一位读者这样说："用同一上下文审查自己不是审查，而是带斜杠命令的确认偏误。"如果代理在编写代码的会话中进行审查，它的上下文包含了塑造代码的全部假设。独立审查者不会拥有这些上下文。这也是有人要求使用不含内置审查步骤的 [implement](https://aihero.dev/skills-implement) 的原因，因为内置步骤会在刚刚写出差异的同一会话中审查代码。独立审查的方式是在干净会话中自行调用 `/code-review`。

**每个工单审查一次，还是最后审查一次？**

两种方式都可行，此技能不会替你决定。逐工单审查会让每个差异足够小，使规格说明方面有明确的规格说明作为检查依据，这是 `implement` 使用的方式。等分支完成后批量审查，则能发现逐工单审查遗漏的工单间交互。如果不确定，可以逐工单审查，并在分支起点上再做最后一次检查。

**我可以相信这些发现吗？**

不能未经检查就相信。子代理输出是假设，不是证据。某个团队报告说，文字审查漏掉了十多个破坏性更改。此技能会原样组合两份报告，或只做轻微整理。它不会对照文件重新验证每一项声明，因此发现可能引用错误位置，或夸大影响。采取行动前先阅读每项发现的引用。技能要求每项发现都附带引用(标准规则、异味及其代码片段，或规格说明行)，这样才能核查。

**为什么我每次运行都会发现新问题？**

每次修复都会增加新的待审查代码，编码标准方面需要判断的部分也会在每次运行时得出不同结果。一位读者描述了这种循环："`/code-review` 和 `/improve-code-architecture` 每次都会发现新东西。我修复后重新运行这些技能，然后又会反复发现新问题。"此流程不保证收敛。将每次审查视为线索清单。处理有引用规则支撑的内容，然后停止。不要循环运行，直到结果干净，因为它永远不会干净。

**它会审查我尚未提交的工作吗？**

不会。它比较 `<fixed-point>...HEAD`。三个点形式从合并基点开始计算，并排除暂存区和工作区更改。如果 `implement` 尚未创建中间提交，审查就看不到即将进入下一次提交的工作。先提交，再审查，然后修补原提交或添加修正提交。

## 正常生效的表现

- 启动任何子代理前，如果引用无效或差异为空，技能会拒绝开始。
- 报告分别以 `## Standards` 和 `## Spec` 标题分成两个区块，而不是合并成一份清单。
- 每项标准发现都指出仓库文件中的规则，或十二种异味之一，并引用对应代码片段；每项规格说明发现都引用规格说明行。
- 结尾摘要分别列出两个维度各自最严重的问题，不强行做单一综合裁决。
- 没有可用规格说明时，规格说明区块会明确说明，而不是列出从代码推断的要求。

## 它在工作流程中的位置

`code-review` 是构建流程后段的审查步骤：`grill-with-docs → to-spec → to-tickets → implement → code-review → retro`。它也可以单独用于你指定的任何分支或 PR。

- [implement](https://aihero.dev/skills-implement) 是最相近的技能。它驱动构建流程，并在提交前将此技能作为最终审查步骤。[implement-spec](https://aihero.dev/skills-implement-spec) 也会在整个集成分支上执行一次同样的流程。
- [retro](https://aihero.dev/skills-retro) 在它之后运行并调整审查。当会话显示审查漏掉某类错误时，`retro` 会提出检查方法或 `CODING_STANDARDS.md` 规则，供编码标准方面读取。
- [pr](https://aihero.dev/skills-pr) 在审查完成的工作提交后撰写拉取请求正文。
- [to-spec](https://aihero.dev/skills-to-spec) 和 [to-tickets](https://aihero.dev/skills-to-tickets) 会生成规格说明方面要对照的文档，因此规格说明含糊时，该方面的审查也会含糊。
- [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 是针对整个代码库的对应工具，因为此技能只检查一个差异。

如果不确定应该使用哪种流程，[ask-matt](https://aihero.dev/skills-ask-matt) 会在整组技能中进行引导。
