## 功能说明

`diagnosing-bugs` 使用六个阶段诊断困难错误或性能退化：建立复现、缩减复现、排列假设、添加插桩、通过回归测试修复、清理。

在**紧凑**的反馈循环建立之前，它不会让代理提出理论：必须有一条已命名且实际运行过一次的命令，它能在_这个_错误出现时失败，并在修复后通过。如果收到错误报告，编程代理通常会直接阅读代码并猜测原因。此技能会阻止这种做法。没有能够失败的命令，就不能进入阶段 2。这正是此技能的用途。循环建立后，后续工作（二分查找、假设检验、插桩）都是机械流程。

## 适用情形

输入 `/diagnosing-bugs`，或符合条件时由代理自行调用。此技能可由模型调用；用户说“诊断”或“调试这个”，或报告功能损坏、抛出错误、失败或变慢时会触发。

困难问题适合此技能：初看无法解决的错误、间歇性偶发错误，或两个已知正确状态之间引入的退化。它有意使用缓慢且彻底的流程，因此不适合你希望在一条消息内得到答案的问题。

| 你的情况 | 使用方式 |
|---|---|
| 能描述具体症状的明确缺陷 | 使用此技能 |
| 端点变慢，或发生了有已知前后状态的耗时退化 | 使用此技能。它有性能分支（测量基准，然后二分查找） |
| “这个代码库的性能瓶颈在哪里？”，没有具体症状 | 不要使用此技能。它诊断一个已知故障，不执行审计 |
| 其他人提供的原始错误报告，尚未确认或记录 | 先使用 [triage](https://aihero.dev/skills-triage) |
| 编写一次性代码来回答设计问题，而不是追踪缺陷 | 使用 [prototype](https://aihero.dev/skills-prototype) |
| 先写测试再构建计划中的行为 | 使用 [tdd](https://aihero.dev/skills-tdd) |
| 错误修复后想知道怎样才能避免它 | 在同一会话中运行 [retro](https://aihero.dev/skills-retro) |
| 没有适合锁定错误的接缝 | 自行启动 [improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) |

## 紧凑循环就是此技能

阶段 1 投入的精力最多，因为它是唯一困难的阶段。技能按大致优先顺序列出建立循环的方法：

1. 在任何能触及错误的接缝处运行失败测试。
2. 针对运行中的开发服务器执行 curl 或 HTTP 脚本。
3. 使用夹具输入调用 CLI，并与已知正确快照进行差异比较。
4. 使用无界面浏览器脚本断言 DOM、控制台或网络。
5. 重放已保存请求、载荷或事件日志，并在隔离环境中运行相应代码路径。
6. 使用一次性测试工具，只启动系统最小子集并调用一次函数。
7. 对“输出有时不正确”的问题运行属性测试或模糊测试循环。
8. 构建可以交给 `git bisect run` 的二分查找测试工具。
9. 对相同输入运行旧版本和新版本并比较结果。
10. 最后才使用[人工参与](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop) Bash 脚本。技能提供 `scripts/hitl-loop.template.sh`：代理运行脚本，你在终端按提示操作，答案会以可解析的输出返回。

目标不是随便有一个循环，而是要**紧凑**：快速（以秒计）、确定性（每次运行结果相同）、明确（断言确切症状，而不是“没有崩溃”），并且代理可以独立运行。30 秒且不稳定的循环几乎不比没有循环好。对于只偶尔出现的错误，目标不是得到干净的复现方式，而是**提高复现率**：重复触发条件、并行运行、增加压力、插入睡眠，直到偶发率足以支持调试。

代理无法建立循环时，技能要求它停止并说明情况，列出已经尝试的内容，并请求访问[环境](https://www.aihero.dev/ai-coding-dictionary/environment)、获取已捕获资料，或授权添加临时插桩。无论如何，它都不得继续提出假设。

## 阶段之间的关卡

这些阶段是关卡，不是检查清单。只有满足具体条件，代理才能进入下一阶段。

| 关卡 | 必须满足的条件 |
|---|---|
| 进入阶段 2 | 已命名的命令已运行，并粘贴了输出；该命令能在此错误出现时失败 |
| 进入阶段 3 | 已复现并缩减复现步骤：每个剩余元素都是复现错误所必需的 |
| 进入阶段 4 | 已提出 3–5 个按可能性排序、可证伪且各自说明预测的假设，并在测试任何假设之前向你展示 |
| 进入阶段 5 | 探测对应具体预测；一次只改一个变量；每条调试日志都有类似 `[DEBUG-a4f2]` 的标签，以便用一次 grep 全部清理 |
| 完成 | 原始复现不再触发，插桩已移除，提交说明写明最终验证正确的假设 |

阶段 5 有一个例外：只有存在**正确接缝**时，代理才会在修复前编写回归测试；此接缝上的测试必须能够在调用位置复现真实错误模式。唯一可用的接缝太浅时，技能会要求代理明确说明，而不是编写造成虚假信心的测试。缺少接缝本身就是一项发现，代理应记录下来，而不是隐瞒。

## 常见问题

**我只想要直接回答，它却在简单问题上触发了。**

这是此技能最常被报告的问题。特别是在 GPT-5.6-Sol 上，用户报告代理面对单纯的问题描述时会触发此技能：“模型反而触发了非常正式的 diagnosing-bugs 技能。随后它会在给出回复或建议之前构造复现场景（通常会构建价值有限的模拟情景）。这导致回复明显延迟。”四位不同用户在[议题 #578](https://github.com/mattpocock/skills/issues/578)报告了同一问题。已接受的修复建议是先采用较轻量的方式，只有问题需要时才进入完整诊断，但该修改尚未发布。此技能针对 Claude Code 的调用行为进行调整，而触发阈值较低的[模型](https://www.aihero.dev/ai-coding-dictionary/model)会过度调用它。修复发布前，可以明确说明你要什么（“只回答问题，不要诊断”），或在[运行环境](https://www.aihero.dev/ai-coding-dictionary/harness)中禁用模型调用。

**我能让它检查代码库并指出性能问题吗？**

不能。它诊断一个你已经能够指出的故障。性能分支适用于有症状的退化（建立基准测量，再二分查找，先测量再修复），不用于主动扫描。有人曾[提出并关闭](https://github.com/mattpocock/skills/issues/431)主动扫描技能的提议，目前没有技能执行此工作。

**它会在编写修复之前停下来询问我吗？**

不会。只有阶段 3 有人工检查点：代理会在测试前向你展示按可能性排序的假设列表；如果你暂时不在，它会继续采用自己的排序。插桩和修复之间没有关卡，因此在你认可根本原因之前，代理就可能开始编写代码。[议题 #124](https://github.com/mattpocock/skills/issues/124)要求增加这个关卡，但仍未解决。需要此关卡时，调用技能时要明确说明。

**我已经对这份错误报告运行 `/triage`。现在是在重复做相同工作吗？**

部分重复，而且两个技能都没有说明这一点。一位读者说：“Triage 的第 3 步基本上是 diagnosing-bugs 第 1 至第 2 阶段的浅层限定版本，但两个文件都没有提及对方。”Triage 会有限度地检查“这确实是错误吗，影响范围是什么”；此技能执行彻底版本。先运行 triage 并非浪费，因为它的验证往往能提供大部分阶段 1 的原始材料。但请预期此技能会完整重复这部分工作，且不会通过交叉引用提示你这一点。

**它粘贴的复现输出会泄露秘密吗？**

有可能。技能要求代理粘贴命令和输出，并要求提供 HAR 文件、日志转储、核心转储等资料，但没有指示代理清理其中的信息。[议题 #674](https://github.com/mattpocock/skills/issues/674) 正是针对这个问题提出防护措施（凭据、令牌、Cookie 和个人信息被复制到聊天、议题或 PR 中）。此议题仍未解决，也未实现。目前请自行负责脱敏，特别是输出将进入公开场合时。

**安全扫描器将此技能标记为高风险。**

Snyk 会标记此技能，但属于误报。此技能是整组技能中唯一一个同时包含可执行 Shell 脚本（`hitl-loop.template.sh`）、运行脚本的指示，以及 curl 开发服务器指令的技能。静态扫描器足以因发布了 `.sh` 文件、要求运行它并进行外发 HTTP 请求而触发。脚本本身约有 30 行 `read -r -p` 提示，会暂停等待用户输入。扫描器评估的是技能**可能**做什么，而不是已经证实的漏洞。

**`/diagnose` 后来怎么样了？**

v1.0.0 将它重命名为 `/diagnosing-bugs`。旧名称不再存在。任何使用 `/diagnose` 的自动衔接内容（包装技能、已保存提示）都需要更新。

## 判断是否有效

- 在提出任何理论之前，它会先展示命令及其失败输出。如果先给出理论，说明技能没有按要求运行。
- 它复现的是你报告的故障，而不是过程中遇到的相似故障。
- 开始猜测之前，它先缩减复现步骤，并能说明剩下每项内容的必要性。
- 测试假设之前，它会展示 3–5 个按可能性排序的假设，每个假设都包含可证伪的预测。
- 新增的每条调试日志都有类似 `[DEBUG-a4f2]` 的标签，宣布完成时，grep 不会找到任何此类日志。
- 提交或 PR 说明会指出哪个假设正确。
- 没有办法通过测试锁定错误时，它会说明情况，而不是编写浅层测试。

## 它在工作流程中的位置

`diagnosing-bugs` 是可独立随时调用的技能。功能损坏时启动它，完成修复和回归测试后结束。它不会保留状态，也不需要事先设置。[ask-matt](https://aihero.dev/skills-ask-matt) 会将“有东西坏了”引导到这里。

有两个相邻技能。[retro](https://aihero.dev/skills-retro) 在它之后运行：修复完成后，在同一会话中询问如何才能避免错误，因为此时会话掌握的信息比开始时更多。`diagnosing-bugs` 不会自行调用 `retro`，因为 `retro` 是由用户调用的。[triage](https://aihero.dev/skills-triage) 则用于处理其他人提交的原始错误报告，在此技能之前运行，并以较浅方式执行同样的前两个阶段。
