## 它的作用

`domain-modeling` 会在设计期间建立并打磨项目的**通用语言**。当术语与术语表冲突时，它会提出质疑；当你使用模糊词语时，它会要求使用精确词汇；它会通过具体情形检验概念之间的关系，直到明确其边界。

它是一项**主动**实践，而不是被动实践。任何技能都可以阅读 `GLOSSARY.md` 并使用其中的词汇。此技能用于*修改*模型，这也是它会打断你的原因。术语确定时，它会在对话进行期间将术语写入 `GLOSSARY.md`，而不是最后再整理出一份整洁的术语表。在最后才写入的术语表只是[会话](https://www.aihero.dev/ai-coding-dictionary/session)摘要；边讨论边写入的版本才是会话的产物。

## 何时使用

输入 `/domain-modeling`，或者当任务符合条件时，由代理自动调用。实际上，自动调用是此技能最薄弱的部分。当 `grill-with-docs` 或 `wayfinder` 要求加载它时，[模型](https://www.aihero.dev/ai-coding-dictionary/model)经常加载 `grilling`，却跳过此技能。如果进行了一次[深入追问](https://www.aihero.dev/ai-coding-dictionary/grilling)，但会话结束时 `GLOSSARY.md` 没有变化，就说明发生了这种情况。将此技能与其他技能一起按名称调用。

当问题出在*用词*时，使用它：

| 情形 | 处理方式 |
| --- | --- |
| 两个人对"cancellation"的含义不同 | `domain-modeling`：选择规范术语，并将其他词列在 `_Avoid_` 下 |
| 三个文件中的"Account"各自有不同用途 | `domain-modeling`：拆分为 Customer 和 User |
| 刚作出难以撤销的架构决定 | `domain-modeling`：如果该决定符合条件，它会提出创建 ADR |
| 模块的*形状*是问题所在：接缝应设在哪里、接口应有多深 | [codebase-design](https://aihero.dev/skills-codebase-design) |
| 想在构建之前审视整个计划 | [grill-with-docs](https://aihero.dev/skills-grill-with-docs)，它会在底层调用此技能 |
| 想查询术语而不是修改术语 | 什么也不用做。读取 `GLOSSARY.md` 文件即可。 |

## 前置条件

事先没有任何前置要求。此技能会写入两个位置，并且只在需要时才创建它们：

- **仓库根目录中的 `GLOSSARY.md`**。第一个术语得到确认时，此技能会创建它。如果根目录存在 `GLOSSARY-MAP.md`，则术语会写入该映射所指向的上下文专属 `GLOSSARY.md`。
- **`docs/adr/`**。第一个符合要求的 ADR 出现时，此技能会创建该目录。

开始前无需准备任何文件，技能也不会预先创建文件。

## 两种产物，两种标准

术语表和 ADR 使用不同标准。人们使用此技能时，大多数问题都源于将两者混为一谈。

| | `GLOSSARY.md` | `docs/adr/NNNN-slug.md` |
| --- | --- | --- |
| 保存内容 | 术语。用一两句话说明某个事物**是什么**，并在 `_Avoid_` 下列出被拒绝的同义词 | 一项决定，用一到三句话说明背景、选择和理由 |
| 写入标准 | 模糊术语变成规范术语 | **全部三项**：难以撤销、没有背景时会令人意外、确实存在取舍 |
| 写入方式 | 当场写入，术语确定后立即记录 | 先提出建议，不默认记录 |
| 绝不保存 | 实现细节、[规格说明](https://www.aihero.dev/ai-coding-dictionary/spec)、草稿区、通用编程概念 | 此会话中作出的每个选择的流水账 |

ADR 的三项标准中任何一项不符合，就不创建 ADR。容易撤销的决定之后可以直接撤销；不令人意外的决定不会引发任何问题；没有真实替代方案的决定，只是在记录你采取了显而易见的做法。

`GLOSSARY.md` 的规则最重要，因为实际使用中最容易违反。**它只是术语表，不包含其他内容。**如果不检查，模型会把"写入 `GLOSSARY.md`"理解为可以保存你的每个答案，文件就会变成持续扩展的规格说明。这是多个模型中最常被报告的技能问题。

## 跨引用，以及跨引用的范围

当你说明某项功能如何运作时，技能会检查代码并指出任何矛盾。"你的代码会取消整个订单，但你刚才说可以部分取消。哪种说法才正确？"在更改语言或代码之前，技能会当面说明两者之间的矛盾。

它会交叉参考**代码**、已提交的 `GLOSSARY.md` 和 ADR，不参考其他内容。它不会搜索 issue tracker。如果团队几个月前曾在已关闭的问题中讨论并解决了术语冲突，技能仍会像首次遇到一样重新提出。[目前有一个未解决请求](https://github.com/mattpocock/skills/issues/717)希望修复此问题。在那之前，可将指示写入技能已经会读取的自有 `docs/agents/domain.md` 中。

## 常见问题

**我的 `GLOSSARY.md` 有 500 行、1,000 行或 3,000 行。我该怎么办？**
文件大小只是症状。问题在于文件包含了实现细节和不应属于术语表的决定。直接下达指示来解决：`/grill-with-docs make my GLOSSARY.md more concise and remove any implementation details from it`。对臃肿文件使用该指示，大部分内容会被移除。只有当文件已经精简，却仍然涵盖两个读者不希望同时处理的领域时，才使用 `GLOSSARY-MAP.md` 将其拆开。将臃肿文件拆开只会得到多个臃肿文件。此技能目前对如何预防文件膨胀的指导还不够有力，相关问题仍然开放。

**为什么历史上曾命名为 `CONTEXT.md`，现在统一为 `GLOSSARY.md`？**
这是整套技能中讨论最多的命名变迁。过去该文件曾命名为 `CONTEXT.md`，其出发点是领域驱动设计(DDD)中的有界上下文(Bounded Context)，由 `CONTEXT-MAP.md` 索引多个上下文的映射体系。然而反对者认为，在智能体开发环境中"所有内容都是上下文"，且若该文件"纯粹用于记录术语表，不包含其他内容"，那么直接命名为 `GLOSSARY.md`(映射文件为 `GLOSSARY-MAP.md`)才更加名副其实、不易引起歧义。目前仓库已全面统一采用 `GLOSSARY.md`；整套技能体系均会查找该文件名。

**`/ubiquitous-language` 去哪里了？**
它已移除，但并没有标记为弃用。它的工作转交给 `domain-modeling`，后者会持续维护整个模型，而不是只在一次对话后导出术语表。词汇规则现在更重要了，而不是不再重要。它会在深入追问、分流和绘制地图的底层运行，而不再是需要你单独记得执行的一步。

**如何为没有术语表的代码库创建术语表？**
明确提出请求，不要等它逐渐积累。文档中推荐的方式是运行 `/grill-with-docs help me scaffold my existing repo with a GLOSSARY.md`。预期会进行较长时间的深入追问。一位用户报告说，术语表整理妥当前回答了 50 多个问题。在棕地仓库中偶尔使用此技能会让术语表建立得太慢。

**我可以保留领域模型，同时使用自己的 ADR 格式吗？**
目前无法轻易做到。术语表部分和 ADR 部分作为一项技能发布，因此如果团队已经采用既定的 ADR 约定(使用不同模板、位置或命名方式)，技能给出的指示就会与团队规范冲突。目前可以在本地复制并编辑技能，或在仓库自己的代理文档中覆盖 ADR 约定。拆分两部分的[请求仍未解决](https://github.com/mattpocock/skills/issues/557)。

**术语表是否真的有价值？它是又一份需要审查的产物，而且可能过时。**
有时没有价值。DDD 越接近实现，就越没有用处。它的价值在上游，体现在名称和概念的一致性，而不是聚合和分层仪式。需要控制同义词的场合是命名边界：模块名称、表名称、状态枚举、问题标题、命令行界面命令。普通文字对同义词的要求低得多。另一种反对意见是，领域术语压缩了*已经共享术语的人类之间*的沟通，而代理对通俗白话的描述也会做出相同反应。按照这种观点，术语表的价值在于让你和审查者理解代理正在做什么，而不是提升代理的能力。只需一天即可完成的构建，可以跳过术语表。未经审查、由代理撰写的术语表比没有术语表更糟糕：它会充斥自信的断言，让之后的会话误以为它们都是真的。

**它能帮我把模糊提示转换成领域语言吗？**
不能，也没有计划创建一项这样的技能。你自己都不理解的领域语言，即使写下来也毫无意义。此技能会在你理解概念后要求措辞准确；它不会发明你并不知道的词汇。另一个相关陷阱是只使用领域词汇，却不建立模型。即使术语选择正确，概念错误也会产生看起来正确、实际却不正确的内容。

## 使用效果良好时

- 当你使用的两个词可能代表不同含义时，它会打断你并询问，而不是自行选择其中一个词然后继续。
- `GLOSSARY.md` 在对话**期间**持续更新，而不是最后一次性更新。
- 对于明天就能撤销的内容，它会拒绝编写 ADR，并指出三项标准中具体哪一项不符合。
- 新条目用一两句话说明事物*是什么*，并在 `_Avoid_` 下列出你决定弃用的词语。
- 代码与表述不一致时，它会引用代码来让你确认。
- `GLOSSARY.md` 经常变短，而不只是不断变长。

## 所在流程

`domain-modeling` 是一项**由模型调用的参考技能**，更多时候它在其他技能的底层运行，而不是独自运行。[grill-with-docs](https://aihero.dev/skills-grill-with-docs) 会通过深入追问过程调用它，[wayfinder](https://aihero.dev/skills-wayfinder) 会在绘制地图时加载它，[triage](https://aihero.dev/skills-triage) 会使用它，让[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)采用项目自己的用词，[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 会在决定确定时调用它。与它最接近的技能是 [codebase-design](https://aihero.dev/skills-codebase-design)。两者一起构成其他技能的词汇层：此技能针对*领域*，另一项针对模块的*形状*。你也可以直接调用它，在正常情况下会加载它的其他技能步骤之前，单独使用领域建模实践。如果你不确定哪项技能适合，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你指路。
