## 功能说明

`tdd` 采用先写测试再实现的方式构建功能或修复错误：先写一个失败测试，只编写足以让它通过的代码，然后处理下一个行为。它包含能让循环产出值得保留的测试标准：好测试的特征、测试位置、模拟的用途，以及会让测试套件失去价值的三种反模式。

它不会在你尚未同意的接缝处编写测试。创建任何测试之前，它会说明计划测试哪些公开边界，然后停下来等待你确认。测试投入有限，这一步能让测试覆盖关键路径，而不是每个边缘情况。`tdd` 也是**参考资料**，不是流程驱动工具。它提供循环规则，由其他人或 [implement](https://aihero.dev/skills-implement) 来运行应用这些规则的[会话](https://www.aihero.dev/ai-coding-dictionary/session)。

## 适用情形

输入 `/tdd`，或符合条件时由[代理](https://www.aihero.dev/ai-coding-dictionary/agent)自动调用，例如先写测试再实现功能或修复错误，或你说"红绿重构"时。

存在要构建的具体行为，且具有输入和可观察的输出，同时你希望测试能够经受重构时，使用此技能。

| 你的情况 | 使用方式 |
|---|---|
| 输入和输出明确的行为(业务逻辑、请求 / 响应协议、转换、验证) | 使用 `tdd` |
| 行为还没有明确规定 | 使用 [to-spec](https://aihero.dev/skills-to-spec)，它会在编写代码前一并约定测试接缝 |
| 真正的问题是接口形态，而不是测试 | 使用 [codebase-design](https://aihero.dev/skills-codebase-design) |
| 已有[规格说明](https://www.aihero.dev/ai-coding-dictionary/spec)或[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)，希望代理运行完整构建流程 | 使用 [implement](https://aihero.dev/skills-implement)，它会逐工单运行 `tdd` |
| 配置、组件连接代码、胶水代码、类型注解、直接委派 CRUD 的代码 | 这里没有适合的技能；请参阅下方未解决问题 |

最后一行指出了真实缺口。技能决定接缝应该放在哪里，但没有任何内容决定改动是否值得进行测试循环。如果在无法依据独立事实来源进行断言的更改上运行它，就会得到重复实现内容的测试。这正是它要警告的同义反复反模式，只是从另一个方向产生。[议题 #746](https://github.com/mattpocock/skills/issues/746) 正在跟踪此问题，目前尚未解决。在它关闭之前，你需要自行判断，或将规则写入 `CLAUDE.md`。

## 前置条件

必须安装 [codebase-design](https://aihero.dev/skills-codebase-design)。`tdd` 以前包含自己的深层模块和接口设计说明；v1.0 中将这些说明删除，改为共用技能，现在 `tdd` 使用它提供的接口设计词汇。除此之外没有其他前置条件。此技能是[无状态](https://www.aihero.dev/ai-coding-dictionary/stateless)的，不会自行写入文件。

## 测试循环和测试接缝

此技能依赖三个术语。

**红绿循环。** 先编写失败测试，再只写足以让它通过的代码。不要提前为下一个测试编写代码。循环中没有重构阶段。技能在 2026 年 6 月删除了这个阶段，因为代理几乎从不执行它，而且将实现和审查放在不同会话中效果更好。重构属于 [code-review](https://aihero.dev/skills-code-review) 的工作。

**纵向切片。** 在一个接缝处写一个测试，再编写最小实现，然后重复。第一个循环是**曳光弹**，用于端到端验证单条路径。相反的方式是横向切片：先编写所有测试，再编写所有代码。批量编写的测试验证的是*想象中的*行为。它们检查事物的形状，而不是用户如何操作，并且在理解实现之前就让你确定了测试结构。

**事先约定的接缝。** 接缝是观察行为时使用的公开边界，无需访问内部内容。此规则没有例外。未经确认的接缝处不得编写测试。在完整流程中，接缝会更早地在 [to-spec](https://aihero.dev/skills-to-spec) 阶段约定："`/tdd` 会被告知只在事先约定的测试接缝处工作；`/code-review` 会检查只使用了已约定的测试接缝。"单独调用时，`tdd` 会直接询问你。

它要避免的三种反模式：

| 反模式 | 表现 |
|---|---|
| 与实现耦合 | 内部函数重命名后行为没有变化，测试却失败。模拟了内部协作者、断言调用次数，或使用数据库查询验证结果，而不是通过接口验证。 |
| 同义反复 | 预期值按照代码的计算方法计算，因此测试必然通过。预期值必须来自其他来源：正确的字面值、计算示例或规格说明。 |
| 横向切片 | 所有测试都在实现代码之前合并。 |

模拟只能用于系统边界：外部 API、时间、随机数，有时也包括文件系统或数据库。绝不要模拟自己编写的模块。

## 常见问题

**为什么它不重构？说明写着"红绿重构"。**

因为重构阶段已被删除，但说明文字尚未更新。删除是有意的：代理几乎从不执行该步骤，而且将实现和审查放在不同会话中效果更好。与其纠结这是否符合教科书中 TDD 的定义，不如关注测试循环是否产生更好的代码。触发词和正文不一致的问题已记录为[议题 #589](https://github.com/mattpocock/skills/issues/589)，尚未解决，因此"红绿重构"仍然可以触发技能。实际执行的是红绿循环，重构交由 [code-review](https://aihero.dev/skills-code-review) 处理。

**它让我选择测试接缝，但我不知道应该选哪个。**

这是此技能最常被报告的摩擦点([议题 #607](https://github.com/mattpocock/skills/issues/607))。提示只会列出候选接缝名称，不会说明每个接缝能发现或漏掉哪些问题，因此你只能在不同名称之间选择。目前没有发布修复。实际的解决方法是在回答前要求代理说明权衡：组件级接缝会漏掉什么，而集成接缝能发现什么，速度又会慢多少。这也是为什么完整流程会在 `to-spec` 中提前约定接缝；此时你能看到完整功能，而不是只看到一个提示。

**技能说明先写红色测试，但它先写了实现。**

这种情况确实会发生。一位用户质问[模型](https://www.aihero.dev/ai-coding-dictionary/model)后，得到一个异常诚实的回答："我知道技能写着‘一次一个测试，并观察它因为正确原因失败’。我读过了，只是下意识采用了平常的习惯。"技能对此承认。没有任何指令能保证代理百分之百遵循要求，而且更严格的措辞会限制代理的创造性，收益却很小。即使代理不严格遵循规则，运行测试循环仍然值得，因为整体结果会更好。如果某个切片必须严格遵循规则，就观察运行过程，而不是相信技能能够强制执行。

**应该先写浏览器测试或端到端测试吗？**

通常不应该，但技能不会阻止。曾有用户报告代理先写了 Playwright 测试，然后在很长的循环中不断运行，并在功能还不存在时得出"测试"坏了的结论。浏览器测试太慢，会让红绿反馈循环失去价值。可以在仓库的 `CLAUDE.md` 中规定行为实现之后再编写浏览器测试。

**`/tdd` 会取代 `/implement` 或课程中的 `/do-work` 吗？**

不会。`/tdd` 记录方法论；`/implement` 是简单的"工作 → 反馈 → 提交"循环，直接替代 `/do-work`。课程中原来的单个 `/do-work` 步骤现在拆分为 `/implement`、`/tdd` 和 `/code-review`。如果你在问某个工单应该运行哪一个，答案几乎总是 `/implement`。

**深层模块和接口设计指南放在哪里了？**

它们在 v1.0 中移入 [codebase-design](https://aihero.dev/skills-codebase-design)，经过通用化，让多个技能共用一套词汇。`refactoring.md` 也在同一时间移除了；重构现在属于 [code-review](https://aihero.dev/skills-code-review) 的工作，该技能包含 Fowler 的代码异味基准。

**它会了解我的其他工单吗？**

不会。针对单个工单运行时，它可能会提出属于同级工单的工作，因为它看不到其他议题之间的关系图([议题 #129](https://github.com/mattpocock/skills/issues/129))。这不是 `tdd` 的职责。提供规格说明和工单会有帮助；更好的办法是事先合理控制工单大小。

## 判断是否有效

- 任何测试文件出现之前，它会停下来，说明计划在哪些接缝处测试，并等待确认。
- 先出现一个测试，测试失败，再编写足以让它通过的代码；只有之后才出现下一个测试，而不是一次出现一批测试，再出现一批代码。
- 测试名称说明功能能力("用户可以使用有效购物车结账")，而不是内部细节("checkout 调用 paymentService.process")。
- 断言中的预期值是可以追溯到规格说明的字面值，而不是按照代码的计算方法重新计算出来的值。
- 内部函数重命名后，测试套件不受影响。
- 只在外部边界(支付 API、时钟)使用模拟，绝不模拟自己的模块。

## 它在工作流程中的位置

`tdd` 在主流程的构建步骤内部运行，不是独立的一步：

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

[to-spec](https://aihero.dev/skills-to-spec) 会事先约定测试接缝，[implement](https://aihero.dev/skills-implement) 会逐工单运行 `tdd`，[code-review](https://aihero.dev/skills-code-review) 之后会检查是否只使用了约定的接缝，并负责执行 `tdd` 不再处理的重构。另一个相邻技能是 [codebase-design](https://aihero.dev/skills-codebase-design)，它为 `tdd` 提供共用的接缝和深层模块词汇。存在具体行为需要构建，但没有完整规格说明时，也可以单独使用此技能。如果不确定哪种技能适合你的情况，[ask-matt](https://aihero.dev/skills-ask-matt) 会为你引导。
