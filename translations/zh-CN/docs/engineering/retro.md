## 功能说明

`retro` 回顾一次编程[会话](https://www.aihero.dev/ai-coding-dictionary/session)，并提出改进代理[环境](https://www.aihero.dev/ai-coding-dictionary/environment)的建议，让下一次运行更顺利。它会读取会话记录(默认读取当前会话，也可根据会话日志读取你指定的会话)，找出代理遇到困难的时刻，并按严重程度从高到低列出候选修复方案。

它修改环境，不修改代码。代理提交了错误、花了二十次[工具调用](https://www.aihero.dev/ai-coding-dictionary/tool-call)才找到某个文件，或审查者漏掉了某条规则，都可以交给它回顾。`retro` 不会直接修复这些问题，而是会询问仓库中哪些因素导致它们发生，并提出能够避免再次发生的检查、指针或标准。它只提出建议。你选定候选项之前不会发生任何更改。

## 适用情形

你需要自行输入 `/retro` 调用此技能，代理不会主动调用。

在工作难度超出预期的会话结束时使用。例如，代理花了太久寻找内容，犯下本可由工具发现的错误，或需要但无法获取某些信息。顺利的会话没什么值得学习，因此发现通常来自困难的会话。如果你想评判会话生成的代码，请改用 [code-review](https://aihero.dev/skills-code-review)。

## 发现应存放在哪里

每个候选项都属于一种类别，该类别决定修复位置：

| 会话中发生的问题 | 修复方式 |
|---|---|
| 代理花了很长时间寻找文件或事实 | 在它已经会读取的文件中添加**导航指针** |
| 代理犯下工具本可发现的错误 | 添加**[自动检查](https://www.aihero.dev/ai-coding-dictionary/automated-check)**：代码检查规则、类型检查、测试、提交前钩子、CI 作业 |
| 审查者漏掉了需要判断的错误 | 在 `CODING_STANDARDS.md` 中添加规则，供审查代理使用 |
| `AGENTS.md` 或 `CLAUDE.md` 内容太多 | 将指导内容移出文件，放入标准文件或检查中 |
| 工具调用的成本与其结果不相称 | 精简工具或替换工具 |
| 指导文件中有许多不会改变任何行为的行 | 删除**无效指令** |
| 代理需要但无法访问某项信息 | 扩大访问权限：将开发服务器日志接入文件，或提供服务的只读访问权限 |

核心原则是标准应由**审查者**负责，而非实现者负责。实施代理承受最大上下文压力，因为它要探索、编写代码并调试失败。审查代理只接收差异。因此，新规则应放在有足够余力执行它的阶段，也就是审查阶段。规则绝不应放在 [AGENTS.md](https://www.aihero.dev/ai-coding-dictionary/agents-md) 中，因为每个会话都会加载它到[上下文窗口](https://www.aihero.dev/ai-coding-dictionary/context-window)中，无论规则是否适用。

写入任何规则之前，`retro` 会先对违规分类。**机械性**违规(禁止使用的 API、导入形式、文件位置规则)要用确定性检查来处理，因为检查可以失败，而标准文件中的一句话不能。只有代码检查器无法强制执行的真正判断事项才会写成文字。如果仓库完全没有护栏(没有提交前钩子，也没有运行代码检查、类型检查和测试的 CI 作业)，`retro` 会将其作为单独发现报告。

## 常见问题

**它会直接编写代码检查规则，还是等我同意？可以让它每次会话后自动运行吗？**

它会等待。`retro` 只提出建议。你选定候选项之前不会更改任何内容，因此它不会自行编辑文件或自动安装钩子。这是刻意设计的。一位用户曾因"自动钩子阻止了正确更改"而蒙受损失，之后提出了这个要求。判断哪些内容值得永久检查需要人工判断，因此此技能由用户调用并保留[人工参与](https://www.aihero.dev/ai-coding-dictionary/human-in-the-loop)。有些用户确实会在每次实现运行后调用它。但顺利的会话没什么值得学习，每次会话后运行大多会产生没人需要的规则。目前没有试运行模式。拟议的检查和其他代码一样，因此让它阻止合并之前，应先在仓库中试用。

**代码检查规则会一直累积吗？它会建议删除规则吗？**

它可以删除部分文字，这是它最薄弱的地方。它可以删除指导文件中的无效指令，也可以把 `AGENTS.md` 或 `CLAUDE.md` 中应放到标准文件或检查中的指导内容移出去。文件很大时，它会建议删除这些内容。它依据单次会话评估这些候选项，因此应将它们视为要经过删除内容后验证效果的候选，而不是既定结论。它不会审查上个月提出的代码检查规则、钩子或 CI 作业。它只能看到一次会话，因此无法判断某条规则现在是否过度触发，或导致规则的错误是否已不存在。你仍须自行清理检查。某条规则频繁触发正常代码，就说明应该删除它。

**它是不是只会为了填满类别而编造通用建议？**

这是对它最强烈的批评。一位用户发现："工作结束后，AI 往往会忘记会话中途遇到的困难，并为了满足回顾类别而编造通用建议。"每个候选项都必须来自会话记录，因此建议会针对该会话。这样既有好处也有代价：它很少编造无关内容，但可能过度重视单次会话讨论的主题。无法追溯到具体时刻的候选项都应舍弃。严重程度排序也只是初稿，因为不显眼但代价高昂的错误可能排在明显但成本低的问题之后。

**我的会话很长。现在运行，还是重新开始？**

默认情况下，它会审查当前会话。这是最佳情况，因为困难点仍在上下文窗口中。如果会话已经离开[有效区域](https://www.aihero.dev/ai-coding-dictionary/smart-zone)，就先[清理上下文](https://www.aihero.dev/ai-coding-dictionary/clearing)，再在新会话中对会话日志里的旧会话运行 `/retro`。

**代理反复犯同一个错误。我应该在 `CLAUDE.md` 中增加一行吗？**

通常不应该，`retro` 对此尤其反对。`CLAUDE.md` 中的一行规则会加载到每个会话，降低文件中其他内容的影响力，并且会随着代码变化而过时。如果错误属于机械性问题，修复方法就是添加会失败的检查。如果错误需要判断，则应写入审查者会读取的编码标准。`AGENTS.md` 和 `CLAUDE.md` 除了导航指针外不应包含太多内容。出于同样原因，`retro` 不是[记忆系统](https://www.aihero.dev/ai-coding-dictionary/memory-system)。它不会存储发生过的事情，而是修改环境以防错误再次发生。

**我的设置提到了 `CODING_STANDARDS.md`，但我没有这个文件。它从哪里来？**

没有技能会随附这个文件。会话首次发现审查者需要判断的规则时，`retro` 会提议创建该文件。你接受后，[code-review](https://aihero.dev/skills-code-review) 会读取它。你已经使用的其他标准文档(例如 `CONTRIBUTING.md`)也会以相同方式被读取。

**它与 `improve-codebase-architecture` 有什么不同？**

输入不同。[improve-codebase-architecture](https://aihero.dev/skills-improve-codebase-architecture) 只需要代码，会寻找结构性改进。`retro` 需要会话历史，并改进代理工作所处的环境，而不是代码。两者可以同时使用，互不取代。

## 判断是否有效

- 每个候选项都指向会话中的具体时刻，而不是通用最佳实践。
- 重复错误会转化为失败检查，`AGENTS.md` 会越来越短，而不是越来越长。
- 如果已有检查却尚未接入，发现应是接入检查，而不是建议新建检查。
- 下一次处理同类工作的会话可以更快找到所需内容。

## 它在工作流程中的位置

`retro` 是主流程链的最后一步，用于回顾整个流程的执行情况：

```txt
grill-with-docs → to-spec → to-tickets → implement → code-review → retro
```

值得从中学习的构建工作完成后，在同一会话中运行它，或指向该会话的日志。顺利的构建可以跳过。

- [code-review](https://aihero.dev/skills-code-review) 是 `retro` 最常调整的审查代理。新编码标准应放在它的标准方面可以读取的位置。
- [writing-for-agents](https://aihero.dev/skills-writing-for-agents) 规定了所有指导文件的写作风格，包括 `retro` 提出的文件和规则；`retro` 会在开始前读取此技能。

如果不确定某种情况适合哪种技能，[ask-matt](https://aihero.dev/skills-ask-matt) 会在整组技能中进行引导。
