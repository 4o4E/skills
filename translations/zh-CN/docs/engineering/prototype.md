## 功能说明

`prototype` 编写**用于回答问题的一次性代码**：状态模型是否合理，或屏幕应该是什么样子。先明确问题，再据此决定要构建什么。即使外观再好，回答了错误问题的原型也是浪费。

"一次性"是对代码**编写方式**的约束，不意味着一定要销毁它。不要添加测试，不要添加运行所需之外的错误处理，不要增加抽象，也不要持久化状态，因为这些都无助于你学习当前要了解的那一件事。只有两样东西会保留：答案会进入真实代码，原型则会提交到主分支以外的分支，作为答案的依据。

## 适用情形

输入 `/prototype`，或符合条件时由[代理](https://www.aihero.dev/ai-coding-dictionary/agent)自动调用。

遇到无法通过讨论解决的问题时，立即使用此技能：例如，无法在脑中掌握边缘情况的状态机，或只有并排查看三个版本才能想象出的页面。[深入讨论](https://www.aihero.dev/ai-coding-dictionary/grilling)会围绕这类问题持续很久。代理换种方式提问，你猜测，范围不断扩大。停止讨论，构建一次性版本，查看实际效果，然后用一句话回答。如果已有功能运行异常，想找出原因，请使用 [diagnosing-bugs](https://aihero.dev/skills-diagnosing-bugs)。原型用于探索要构建什么，不用于查明已构建功能为何故障。

有时即使你没有主动选择，也会来到此处。[wayfinder](https://aihero.dev/skills-wayfinder) 会在计划图中创建 `prototype` 决策[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)，由你使用此技能处理其中一个工单。

## 两个分支

问题决定采用哪个分支，而两个分支会产出不同成果：

- **"这套逻辑 / 状态模型是否合理？"**：生成一个**可分享的 HTML 单文件**。这是一个独立页面，无需构建，也无需服务器，任何人都可以双击打开。页面包含带标签的状态面板，每次点击后重新呈现；用户可以按任意顺序尝试模型的自由操作按钮；还包含带标签页的**引导流程**(每个标签页展示一种情境，下方按顺序排列要点击的按钮)。所有内容都使用领域语言，因此你可以交给设计师、产品经理或领域专家，让他们亲自尝试模型。页面背后的逻辑是一个简洁的纯模块(reducer、状态机、函数集)，其中没有 DOM 代码，因此可以将经验证的版本直接并入真实代码。
- **"这个页面应该是什么样子？"**：在同一条路由生成多个**截然不同的**用户界面方案，通过浮动底栏和 `?variant=` URL 参数切换。多个方案必须在结构上不同，而不只是颜色不同；三个略作调整的卡片网格毫无价值。应尽可能将它们放在真实页面中，使用真实数据和真实信息密度，因为在空白页面上评估的任何方案看起来都不错。

两种原型都将状态保存在内存中，无需任何设置，并且每个步骤后都会显示完整状态。一旦你开始加固原型(添加测试、连接真实数据库、泛化以适应将来可能需要的情况)，就已经不再制作原型。

## 原型是一手资料

完成的原型会留下两样东西，并分别存放到不同位置。

将**答案**(结论以及它解决的问题)记录到永久位置，例如提交说明或实现 issue。只有当实验结论导致人工决定时，才通过项目已安装的 OpenSpec 工作流记录该决定。主分支保留答案，并将其体现在真实代码中。

**原型**是答案的可运行证据，不应删除。也不应将它放在主分支，因为没有人会维护它，而且它很快就会过时。因此，将它提交到主分支以外的临时 `prototype/<name>` 分支，永不合并；并在实现 issue 中留下指向该分支的[上下文指针](https://www.aihero.dev/ai-coding-dictionary/context-pointer)。这样主分支保持整洁，接手工作的下一位也能找到并重新运行原型。

## 常见问题

**等等，原型不应该删除吗？**

现在不再删除。过去的流程是：构建原型，保留答案，丢弃代码。对此最强烈的反对意见与速度无关，而是：*谁会在下一个[会话](https://www.aihero.dev/ai-coding-dictionary/session)中接手工作，他们可以依据什么继续？* 原型的文字摘要会丢失使原型有说服力的内容。因此，此技能现在将原型视为[一手资料](https://www.aihero.dev/ai-coding-dictionary/primary-source)。原型会提交到主分支以外的 `prototype/<name>` 分支，实现 issue 会指向它。更改的是代码所在位置，而不是制作原型的纪律；原型仍然不会合并到主分支。

**以前不是构建终端应用吗？现在它在哪里？**

逻辑分支现在会生成一个可分享的 HTML 单文件。只有已克隆仓库且安装运行时的人才能操作终端应用，因此设计师、产品经理和领域专家都可能无法参与，而原型正需要他们的意见。一个双击打开、通过电子邮件发送后仍可运行的独立文件，任何人都能操作。底层的纯逻辑模块没有变化，仍然是应移入真实代码的部分。

**代理建议我运行 `/prototype`，但我其实应该开始实现。**

这是已知的命名问题。不熟悉工作流程的代理看到通用且吸引人的"prototype"一词时，会认为工单建立后理所当然应该采用这个步骤。因此，即使设计已经在对话中确定，代理也可能主动推荐它。如果你已经知道要构建什么，下一步应是按工单使用 `/implement`。只有存在尚未解决的具体设计问题，而且讨论无法解决时，才使用原型。

**我应该在构建任何生产功能之前先制作整个应用程序的原型(例如向潜在客户演示)吗？**

那是恰好与此技能同名的另一种成果。此处的原型只针对一个问题，而"整个应用程序是什么样子？"不是单个问题。完整应用原型没有自然停止点，因此会逐渐变成生产应用：清理阶段永远不会发生，而且在原型规则下编写的代码(没有测试，没有错误处理)会直接面向用户。如果需要销售演示，就有目的地构建演示，并明确说明任何部分都不能用于生产环境。如果需要解决设计问题，就把范围缩小到该问题。

**我如何在单独会话中运行它？**

原型放在自己的目录中，会生成大量你不想带入提问会话的[上下文](https://www.aihero.dev/ai-coding-dictionary/context)，因此应在其他位置运行，只带回答案。使用 [handoff](https://aihero.dev/skills-handoff) 将工作交给那个会话，再取回答案。

**这难道不是消耗 token 最快的方式吗？**

如果你对本可通过讨论回答的问题制作原型，或让单个原型扩展到整个功能，就可能如此。重要的比较不是 token 和零，而是用多少[token](https://www.aihero.dev/ai-coding-dictionary/token)换取正确状态模型，避免等到状态模型已经被生产环境的调用方使用后才发现错误。问题应保持明确，运行应简短，这样花费才合理。

## 判断是否有效

- 你可以用一句话说明原型要回答的问题，并且它写在演示开头，而不只是存在脑中。
- 不读代码的人也能操作逻辑演示。他们打开文件，在引导流程标签页中按按钮，并用自己的话描述看到的内容。
- 有人说"等等，这不应该发生"或"咦，我以为 X 会不同"。这正是原型要发现的想法错误。
- 用户界面方案在布局和信息层级方面存在差异，而不只是颜色和文案；你收到的反馈是"我想要 B 的页眉和 C 的侧栏"。
- 原型在一次工作时间内完成。如果一天后还在制作，说明问题太大，应拆分问题。
- 完成后，主分支包含决策，不包含原型；实现 issue 指向仍然保存原型的分支。

## 它在工作流程中的位置

`prototype` 是随时可用的独立技能：使用它解决一个设计问题，然后继续原有工作。另一个技能也会运行它。

最常调用它的是 [wayfinder](https://aihero.dev/skills-wayfinder)。wayfinder 计划图由**决策工单**组成，而 `prototype` 是工单可以采用的四种类型之一：当阻塞性问题是"外观应如何？"或"行为应如何？"，而讨论无法解决时，就采用这种工单。讨论含糊时，wayfinder 会创建具体内容以供反馈，此技能则负责构建该内容。答案会解决原型工单，计划图会把原型链接为资料。

其他相邻技能分别位于此技能的上游和下游。[grill-me](https://aihero.dev/skills-grill-me) 和 [grill-with-docs](https://aihero.dev/skills-grill-with-docs) 负责回答可讨论的问题；无法通过讨论解决的问题会交给此技能处理，随后用一句话将答案带回访谈。下游方面，经验证的状态模型或用户界面方向会成为 [to-spec](https://aihero.dev/skills-to-spec) 的已确定输入，它可以直接嵌入原型生成的高信息量片段，而不是改用文字说明。其他任何情况都可以通过 [ask-matt](https://aihero.dev/skills-ask-matt) 在整组技能中进行引导。
