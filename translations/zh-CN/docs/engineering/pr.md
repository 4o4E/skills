## 功能说明

`pr` 规定拉取请求正文的形式：用**摘要**展示更改，用**证据**说明它有效，并通过**合并风险**说明合并风险。它是格式参考，不是工作流程。它不会推送分支、打开 PR，也不会决定 PR 应包含什么内容。它会在[代理](https://www.aihero.dev/ai-coding-dictionary/agent)编写正文时告诉它正文应当是什么样子。

摘要应使用图示，而不是段落。常见 PR 正文会用文字叙述差异。此技能选择能清楚表达要点的**最精简视图**(伪代码、调用树、组件树、文件树、Mermaid 图或有结构的差异)，并保持周边文字简短。审查者已经打开了差异，因此正文应先让他们看到结构，再阅读差异。

## 适用情形

输入 `/pr`，或代理在编写 PR 正文时自动调用。

| 你的情况 | 使用方式 |
|---|---|
| 分支已经准备好，需要让审查者快速浏览的正文 | `pr` |
| 代码已编写，但还没有人审查 | 先使用 [code-review](https://aihero.dev/skills-code-review)，再使用 `pr` |
| PR 已打开，正在收到审查意见 | 此技能组中暂时没有适用技能；`pr` 只编写正文 |

## 模板

按以下顺序分为三个章节：

- **摘要**：一个或多个小型图示，每个图示放在它所支持的简短文字旁边。使用一种，有时使用几种，很少全部使用。只保留审查者需要了解的调用、文件、属性和边界。
- **证据**：展示更改前后的情况。对于视觉更改，如果[环境](https://www.aihero.dev/ai-coding-dictionary/environment)支持截图，截图是最有力的证据。否则，使用伪代码准确展示之前失败、现在通过的测试，或展示有所变化的控制台输出。
- **合并风险**：说明更改属于**单向门 (One-way door)**还是**双向门 (Two-way door)**，以及**影响范围 (Blast radius)**。双向门容易撤销；单向门(破坏性迁移、移除公开 API、难以撤销的决策)则不容易撤销。影响范围说明如果更改有误，哪些内容可能发生故障：布局变化、API 使用方、移动设备响应式布局等。

单向门或双向门是正文的关键思想。它将"合并安全吗？"从直觉判断变成明确说法，让审查者可以反驳。它也会告诉审查者应将[人工审查](https://www.aihero.dev/ai-coding-dictionary/human-review)投入在哪里。影响范围较小的双向门可以快速浏览；单向门则要仔细阅读。

## 常见问题

**我能相信代理对操作风险的判断吗？**

不能盲目相信，而这正是明确陈述判断的意义。编写更改的代理也负责评估风险，因此如果它说"低影响范围的双向门"，就更要谨慎。差异也经常隐藏了更改能否撤销这一点。一位用户说："回滚提交不能撤回已经发出的一批电子邮件。"而带功能开关的发布，在首次向新格式写入数据前都保持双向操作。此技能为代理提供定义(破坏性操作和难以撤销的决策属于单向门)，而不是检查清单，因此要仔细检查"合并风险"一行。两点会有帮助：确保代理拿到[工单](https://www.aihero.dev/ai-coding-dictionary/ticket)或[规格说明](https://www.aihero.dev/ai-coding-dictionary/spec)，而不只是差异；并在仓库代理文档中写明仓库始终视为单向门的更改(数据库结构迁移、任何对外发布或删除操作)，让代理在判断前能够读取。

**它会为我打开 PR 吗？**

不会。`pr` 只负责正文。[implement](https://aihero.dev/skills-implement) 最后会提交到当前分支。创建能打开 PR 的技能或选项(例如 `/to-pr`，或让 `implement` 打开 PR 而不是提交)的提议仍未定案。一位用户的解决方法是在本地覆盖 `implement` 技能，用一句话指示它打开 PR。[implement-spec](https://aihero.dev/skills-implement-spec) 是例外：如果议题跟踪系统通过 PR 关闭工作，或你提出要求，它会打开草稿 PR。由于 `pr` 可由模型调用，代理在你要求打开 PR 时会使用这种正文格式。

**它是不是会生成另一大堆文字和图示？**

此技能就是为避免这种情况设计的，但仍有可能发生。用户对代理编写的 PR 正文有一致抱怨："摘要太长，我只需要知道改了什么、如何验证、可能会破坏什么，以及合并是否安全。"此技能要求代理省略前言、保持文字简短并选择最精简视图，通常只使用一个图示，很少全部使用。如果仍然得到一堆图示，就是代理没有遵循要求。如果正文太长是因为差异太大，则问题出在 PR 大小，`pr` 不会帮你拆分它。

**我的仓库已经有 PR 模板。哪个优先？**

默认情况下，两者都不优先。`pr` 使用自己的模板，不会查找 `.github/pull_request_template.md` 或类似文件。几位用户要求技能采用仓库模板。如果不做设置，代理会收到两个针对同一文档的冲突指令。可以在仓库代理文档中解决，例如填好仓库模板，再将摘要、证据和合并风险写在其结构下。

**输出是 HTML 吗？为什么 Mermaid 图没有渲染？**

输出是 Markdown 格式的 PR 正文，不是 HTML 页面。GitHub 和 GitLab 可以渲染 PR 描述中的 Mermaid 代码块，但终端不能，因此代理在本地展示正文时，图示会显示为原始文本。使用命令行运行环境的用户曾通过 ASCII Mermaid 渲染器解决此问题，或要求代理将 HTML 版本附加到 PR。Mermaid 是六种视图之一。调用树、文件树或有结构的差异在任何地方都能阅读。

**它能整理返回的审查意见吗？**

不能。它编写正文后就结束。用户多次要求提供方法，判断其他开发者或审查机器人返回的评论哪些值得处理，哪些不算问题。此技能不处理这些工作。

**PR 更改后，它会同步更新正文吗？**

不会。它只会在某个时间点编写正文；审查期间发生更改的 PR 会让正文过时。大幅修改后，要求代理重写正文。代理会再次编写 PR 正文，因此仍会使用同一格式。

**我的更改没有用户界面。证据应该写什么？**

除截图以外的任何证据。只有更改有视觉效果时，截图才是最有力的证据。对于迁移、后台作业或重构，证据是更改前失败、现在通过的准确测试，或发生变化的控制台输出。单独说"测试都通过了"是声明，不是前后对比。

**可以标记正文由大型语言模型撰写吗？**

此技能本身不会这样做。一位用户采用的做法是在仓库代理文档中长期规定，代理撰写的每个议题、评论和 PR 都以披露说明结尾。这条规则应放在仓库中，涵盖代理发布的所有内容，而不是放在某一类文档的模板中。

## 判断是否有效

- 不打开差异，只看摘要图示就能知道 PR 更改了什么。
- 正文没有前言，从摘要标题直接开始。
- 证据章节展示更改前后的情况，而不是声称测试通过。
- 每个 PR 都说明操作方向和影响范围；单向门的更改会让你放慢速度仔细检查。

## 它在工作流程中的位置

如果构建工作通过拉取请求发布，`pr` 位于审查与回顾之间：`to-spec → to-tickets → implement → code-review → pr → retro`。它可以由模型调用，因此代理在该流程之外编写 PR 正文时也会自动触发。

- [code-review](https://aihero.dev/skills-code-review) 在它之前运行，因为 PR 正文应说明已经审查过的差异。
- [implement](https://aihero.dev/skills-implement) 生成正文所描述的提交。

如果不确定应使用哪种技能，[ask-matt](https://aihero.dev/skills-ask-matt) 会在整组技能中进行引导。
